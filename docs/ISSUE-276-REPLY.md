感谢反馈，也谢谢你把 `bili.log` 的数字贴出来。你最后那句追问「换号是否应该会丢缓存」是对的，
但「丢上下文」和「丢缓存」是两件不同的事，混在一起就会反直觉。分开说：

## 一、换号不丢上下文

模型看到的对话历史（messages 数组）在你换号的那一刻**一个字节都不会变**。
插件是先构造好完整请求体，再挑账号的；首发、失败转移、重发用的都是同一份 body，
换掉的只是「谁付钱」。所以你感觉「上下文丢得多」，不是换号把历史丢了。
仓库里能解释这个感觉的是另外几件事，都跟账号无关：

- 跨区域（国内/国际）时，模型自己过去的 thinking 会被拍平成普通正文——在
  `workbuddy` / `workbuddy-global` 两个路由之间重放时，宿主写的 provider 是路由名，
  和 adapter 用的模型身份不一致，于是「同一个模型」判不出来。这不是丢消息，但会让
  模型看起来像忘了自己之前的推理。
- 历史折叠只在**上游明确报超限**时才会发生，按块摘要后重发。
- 会话中途工具注册表增删工具，会改写 system 段，导致跨轮前缀断裂（实测某些 turn
  命中率直接归零）。这是目前查到的压低命中率的最大单一成因。

## 二、换号丢的是「缓存计价」，而且按模型而异

这部分你的直觉是对的，但不是所有模型都这样。仓库里之前测过，这次又补了一次：

| 模型 | 换号代价 | 证据 |
| --- | --- | --- |
| `deepseek-v4.1-flash` | **换号付一次完整冷前缀** | A 号预热 97.4% → B 号同字节 0.0% → A 号事后 97.3%；今天用全新随机正文复测，B 首次 0/5 命中、A 事后 5/5 命中 |
| `glm-5.2` | **换号零代价** | 两个不同账号，B 的首次请求 5/5 命中，与 A 号同量（4096） |
| `minimax-m3.1-flash` | 连同账号都不复用缓存 | 同凭据同字节连发，命中率 0–2% |

所以准确说法是：**「缓存按账号隔离」既不是通用事实，也不是错觉——取决于模型。**
你用的恰好是 `deepseek-v4.1-flash`，属于会隔离的那一类，所以你观察到的方向没错。

## 三、但它不足以解释你看到的整体命中率

你贴的数字里「缓存未命中合计 1.97%、归因于换号 0.95%」本身就说明换号不是主因。
按实测换号频率换算，命中率仍有约 94%；要靠换号把命中率压到 70%，得**每 3.8 个请求
就换一次号**——而账号池只在账号被排除、失败转移或你手改顺序时才换号。

你提到「统计里缓存命中率还挺高但反直觉」，这两件事其实能并存：
用量页那个百分比是**整条日志的累计加权平均**，不是瞬时值。一次换号只让一个请求变冷，
后面几十个高命中轮次会把它稀释掉。再加上上面说的模型差异——换到不隔离的模型上时，
命中率照样高。

## 四、比「粘账号」大一个量级的杠杆

同一账号、同一模型，只把 `X-Conversation-ID` 从「每请求现生成」改成「稳定」，
warm 命中率配对平均差 **+91.4 个百分点**（95% 区间 [87.3, 95.4]，维护者独立复现
+87.1pp [81.9, 92.0]）。这个效应比换号大一个数量级。
**这个开关（`stableConversationId`）从 5.24.15 起已经默认开启**，如果你还在旧版本，
先升级，效果比按会话固定账号更直接。

## 五、关于「按会话固定账号」这个需求

仓库里目前**没有** session → account 的亲和实现：账号池每个请求都会重新排序，
不记上次选了谁。你现在的 `orderAccountIds` 手排顺序能钉住，但那是全局钉死，
代价是池子的分摊和容错都作废。

你的提议（同一会话固定账号，故障时才转移）在方向上是合理的，但要提醒两点：

1. 它能不能省积分，**必须先做单变量对照**：固定模型、固定 `X-Conversation-ID`、
   固定前缀，只让账号变这一个变量。你那份日志的归因是按 `cached` 常数指纹推的，
   不是按账号维度实测——`[acp-usage]` 日志里不记「本次用了哪个账号」。
2. 上游到底是「缓存键按账号分区」还是「路由亲和」，客户端侧分不出来
   （仓库所有相关文档都明确 `MECHANISM_PROVEN = false`）。所以这个功能即使做了，
   也只能说「观察到相关」，不能保证在所有账号/模型/时间段都省。

如果你想自己验证在**你的账号和模型**上换号的代价，仓库里有现成脚本：

```bash
node scripts/probe-account-cache-isolation.mjs --model deepseek-v4.1-flash --rounds 5
```

它会挑两个能真正完成请求的账号，每轮换全新随机正文、预热到确认命中再去问另一个号。
注意：它只读账号状态、不改设置，但会消耗少量积分（约 8k token 的短 completion × 若干轮）。

## 六、总结

- **丢上下文**：误解，换号不改请求字节。
- **丢缓存**：deepseek 上成立（今天已复测确认），glm-5.2 上不成立，按模型分述。
- **省积分的大头**：先确认已是 5.24.15+（稳定会话头默认开），再看混用模型、
  工具注册表中途变更、trae 通道不报缓存这几件事——它们才是量级更大的成因。
- **按会话固定账号**：可以考虑，但它是新功能，且「能省多少」目前没有实测；
  建议先跑上面的脚本拿到你自己的数字，再决定值不值得做。
