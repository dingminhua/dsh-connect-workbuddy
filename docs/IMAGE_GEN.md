# 生图 / 改图工具：`workbuddy_draw_image`

> 日期：2026-10-21 取证；2026-10-25 跨区复测 + 改图接入 · 取证与联调时版本：4.13.2（`upstream/main` = `dfe7ab3`）
> 工具名：`workbuddy_draw_image` · 国内区与国际区都能注册（逐区打开「允许模型自主生图」）
> 真实成本：**按区不同**——国内区实测 **5.71** 积分/张（一次真实联调花掉 5.71），国际区实测 **0.03** 积分/张

## 结论

1. **WorkBuddy 的生图能力是官方 CLI 的一等能力，不是网页端私有的。** 端点
   `POST {chatBase}/v2/images/generations`，请求体只有 `model` / `prompt` / `size`
   （`n` 仅 hunyuan 系带），响应是 `{code, msg, requestId, data:{created, data:[{url}],
   usage:{credit}}}`。国内区 `chatBase` 是 `https://copilot.tencent.com`
   （`www.workbuddy.cn` 是同集群另一入口，两处都答 200）。
2. **产物是 24 小时有效的 COS 签名 URL，不是 base64。** 实测响应里
   `data.data[0].url` 指向 `ai-corpus-backup-1258344699.cos.ap-beijing.myqcloud.com`，
   带 `q-sign-time`（起止各 24h）。插件把这个 URL 原样交给模型与用户，并在返回值里
   写明「约 24 小时失效，要长期保留请及时下载」。
3. **两个区都有生图模型，但它们是两个不同的模型。** 国内区 `/v3/config` 的 61 条模型里
   `hunyuan-image-alpha`（`text-to-image`）与 `hunyuan-image-alpha-edit`（`image-to-image`）
   各带一个标签；国际区 29 条模型里 `hy-image-3.5` **同时**带 `text-to-image` 与
   `image-to-image`。所以工具**两个区都注册**，用哪个区由「哪个区既启用了供应商、又打开了
   「允许模型自主生图」」决定，两区都符合时**优先国内区**（这是唯一向后兼容的顺序：本功能
   此前只能走国内区，升级不能悄悄把老用户的支出挪到另一个网关）。两区的媒体模型目录**完全
   不重叠**，**5.71 与 0.03 是两个模型 × 两个区域共同变化的结果，不是同一张图的跨区差价**；
   两个区的积分池也各自独立，两个数字之间没有任何汇率含义。
4. **模型目录要多读一次同一份文档。** 生图工具需要 `data.models` 里的媒体标签，
   而聊天目录投影时会把它们丢掉，所以它**另外发一次只读 GET** `/v3/config`（国内区
   同样走 `/v3` → `/v2` 降级，与聊天目录一致），工具侧对结果做 5 分钟缓存。它只读、
   不花积分，但每次冷缓存确实多一次请求——如实记在这里，不要写成「零新增请求」。
5. **它是「花钱」的工具，所以按花钱的工具对待。** 缺省即**独占执行**
   （`isConcurrencySafe` 不声明），失败后 **30 秒冷却**，并且工具描述里直接写明两区单价
   （国内版约 5.71、国际版约 0.03 积分/张），让模型和用户都知道「这一张多少钱、不要为了
   试错连续调用」；真实扣费仍以返回的 `credit` 为准。**冷却只看「请求是否真的发出去了」**：
   读目录失败、参数写错、未登录都没花钱，不冷却。

## 工具契约

| 项 | 值 |
| --- | --- |
| 名称 | `workbuddy_draw_image` |
| 参数 | `prompt`（必填，非空字符串）、`size`（**必填**，`宽x高` 或 `auto`；越界不报错而是被等比缩/放到合法范围，见「尺寸与比例」）、`model`（可选，一般留空）、`image`（可选，**字符串数组**，见「改图」）。参数一律「按类型填对」：`size: 1024`、`model: [...]`、`image: 123`、`image: "a.png"`（漏了数组）、`ratio` / `n` / `return_base64` 这类本工具没有的字段，全部 `INVALID_ARGS` 且不发请求，不会静默回落默认值或切换模式 |
| 输出 | `url`、`mode`、`region`、`size`、`model`、`prompt`、`hint` 必填；`credit`、`path`、`requestedSize` 可选。`requestedSize` 只在尺寸被工具缩/放过时出现，是模型原本写的值——有了它，「用户要 4096x4096、实际出 2048x2048」这件事才能被程序识别，不必正则抠 `hint`。`region` 是 `cn` / `global`，`size` 是规整后的小写 `宽x高`——「这次走的哪个区、出的多大」必须能被程序读，不能只写在 `hint` 散文里（子代理冷读明确指出过这一点） |
| 超时 | 180 000 ms（实测单张 12.9–38.7 秒，留足余量） |
| 执行模式 | 独占（不声明 `isConcurrencySafe`） |
| 注册条件 | 宿主有 `tools` 服务，且**至少一个区**既启用了供应商（`regionEnabled`）又打开了该区的「允许模型自主生图」；两区都符合时取国内区 |

`model` 填了但目录里没有时**直接报错**并列出可用模型，不会把不存在的模型 id 发上去
换一个上游 404——那样报错只会是「route config not found」，读者无从知道是名字写错了。

## 尺寸与比例

`size` 最终就是上游的 `size` 字段（`buildImageBody` 不做任何换算、不缩放、不降采样），
但在发请求前会先过两道本地处理，**职责分开**：

1. `parseSizeSpec()` 只管**格式**：只收 `宽x高` 的像素写法（`x` / `X` / 全角 `×` 都认，
   规整成小写 `x`）或 `auto`，宽高必须是正整数。宿主把 `parameters` 原样投影给模型、
   **不代校验**，schema 里的 `pattern` 只是一句提示，`"2K"` / `"1024*1024"` / `"大图"`
   照样会进到 execute 里；不拦就会白打一次扣积分的请求，再拿回一个语焉不详的上游参数错误。
2. `planImageSize()` 只管**范围**：越界不报错，而是 `fitIntoRange()` 等比缩/放到合法范围后
   照常出图，并把「动过什么」写进 `hint`、把原值回带成 `requestedSize`。

比例完全由宽高决定。

`size` 是**必填**，没有默认值：此前不填会静默按 `1024x1024` 出图，于是「什么都没写、
让它自己猜」成了模型的默认行为——用户要竖版壁纸也拿到方图，而且整条链路里没有一处
能指出「比例是在这一步丢的」。比例是用户的诉求，不该由实现替它猜。

上限是**总像素约 419 万**（不是长边、也不是固定白名单），2026-10-25 逐档实测得出：

| 请求尺寸 | 结果 | 实际输出 | 像素 |
| --- | --- | --- | --- |
| `1024x1024` | ✅ | 1024×1024 | 1.05 MP |
| `1024x1536` | ✅ | 1024×1536 | 1.57 MP |
| `1536x1024` | ✅ | 1536×1024 | 1.57 MP |
| `2048x1152` | ✅ | 2048×1152 | 2.36 MP |
| `2048x1536` | ✅ | 2048×1536 | 3.15 MP |
| `2560x1440` | ✅ | 2560×1440 | 3.69 MP |
| `2560x1600` | ✅ | 2560×1600 | 4.10 MP |
| `2048x2048` | ✅ | 2048×2048 | 4.19 MP |
| `2560x2560` | ❌ 拒绝 | — | 6.55 MP |
| `3072x3072` | ❌ 拒绝 | — | 9.44 MP |
| `4096x4096` | ❌ 拒绝 | — | 16.8 MP |

关键结论：**输出是真实像素，不是把大图悄悄压回原生尺寸再放大**。`2560x1440` 与
`2560x1600` 下载回来核过实际宽高，与请求一致，画面里的刻度、文字纹理是独立线条而非插值
（`2560` 档 PNG 约 4.5 MB）。被拒的尺寸是**直接报参数非法**，不会退回一个较小尺寸——
所以工具描述里必须写清上限，否则模型会往 4K 上撞。

按用途选（都在 419 万像素以内）：

| 用途 | `size` | 实测状态 |
| --- | --- | --- |
| 方图（默认）/ 头像 / 方块素材 | `1024x1024`，大图用 `2048x2048` | 两者都实测通过 |
| 横图 / 封面 / 宽幅 | `1536x1024`，大图用 `2048x1536` | 两者都实测通过 |
| 桌面壁纸 16:9 | `2560x1440` | 实测通过 |
| 打印 / 详情图 4:3 | `2048x1536` | 实测通过 |
| 手机竖屏壁纸 / 竖版海报（小） | `1024x1536` | 实测通过 |
| 手机竖屏壁纸（大） | `1440x2560` | **未单独实测**：与已通过的 `2560x1440` 像素数相同、只转 90°，按像素阈值推断可用；若被拒就先退回 `1024x1536` |

> 竖版大图那一格是**推断不是实测**——为了不把「没跑过的尺寸」写成结论，工具描述里给的是
> 通过实测的宽高（`2048x2048` / `2560x1440` / `2560x1600`），`1440x2560` 只作为
> 「手机竖屏」的推荐出现在本节，并明确标注了它的证据强度。

写进工具描述时**必须把这几种比例都点出来**：此前这里只给了一个 `1024x1024` 的例子，
模型据此把「形如 1024x1024」读成「只能出方图」，用户要竖版也只能得到方图——这不是上游
的限制，是提示词给人造成的错误先验。三档基础尺寸（`1024x1024` / `1024x1536` / `1536x1024`）
照抄官方 CLI `ImageGen` 的 `.describe()`（原文 `Image size in pixels, e.g. "1024x1024",
"1024x1536", "1536x1024"`），大图档位则是上述实测补上的——官方 schema 里没有这些例子。
描述里还并排给出 `2560x1440`（16:9 桌面）与 `1440x2560`（9:16 竖屏）这一对同像素数的
横竖写法：只给「边长 512–2560」这条规则而不给同像素的横竖对照，模型仍会把竖版写成方图。

**描述里不再列被拒的尺寸**（此前的 `2560x2560` / `3072x3072` / `4096x4096` 都被删了）：
模型会照抄示例里的形状乃至数字，"这些数字都失败"在它读来约等于"这个参数能写 4K 尺寸"。
被拒清单只留在报错文案与本文档里。`size` 参数本身现在只说两件事：**格式**（「数字 +
一个小写 x」或 `auto`；用户说的档位词、比例词先按正文的表换成像素数）与**上限**
（两条边各 512–2560、乘积 ≤4,194,304），并明说「写超了不会报错，工具会等比缩/放」。
第十二轮把旧句「这是上限不是格式限制」删了——它同时出现在 pattern 与「极端比例本地
报错」旁边，两个意思互相削弱；改成一句具体动作：「写超了不会报错，工具会缩」。
同理，**行为指令要写在工具 description 里**：「用户要竖版 / 手机壁纸 / 封面时改 size 的
宽高，不要只在 prompt 里说」。之前这条只埋在 `size.description` 里，模型读工具描述就
决定怎么填参数，根本没读到它。

**必填只解决了一半：还要替模型回答「用户没说尺寸时填什么」。** 把 `size` 设成必填，
只是把「不填就出方图」换成了「不填就报错」——用户说「画一只猫」时，模型仍然得自己
挑一个数字，而描述里如果只教换算表（16:9 写 2560x1440、9:16 写 1440x2560），它就
只能瞎猜一个，或者干脆空着撞 `required`。所以描述里直接给了用途对照：聊天配图
`1024x1024`、方图大图 `2048x2048`、横图 `1536x1024`、桌面壁纸（16:9）`2560x1440`、
手机壁纸（9:16）`1440x2560`，并写明「用途不在表里就按方向兜底，方向也看不出就用
`1024x1024` 并说明这是默认值」。**顺手掐掉最像的那条歧路**：
用户说「2K 横图」写 `2560x1440`、「2K 竖图」写 `1440x2560`，不是 `2048x2048`——后者
格式合法、schema 拦不住，但方向就错了（方图当横图）。

**「4K」直接给本工具的最大档，外加一句必须转述的说明。** 这一格改了三轮，每一轮都是
被上一轮的具体后果推翻的：

1. 让模型把「4K」换成本工具的最大档 → 两个评审子代理都证明这一步模型算不好，而且
   「4K 与 2K 降级到同一档」会让「4K」变成没有指称的词。
2. 改成「照写 `3840x2160` / `2160x3840` / `4096x4096`，越界由工具缩」 → 第九轮对抗
   评审指出**这三条全部越界**，照字面走的结果是 4K 档整体退化成 2K 档，而且每次都要
   触发一次缩放提示；又因为「命中一条就停」，用途兜底那阶的 `2560x1440` 永远轮不到。
   等于用一个必然越界的中间值换一次必然发生的降级说明。
3. 现在档位词那阶（第 ③ 步）直接写 `2560x1440` / `1440x2560` / `2048x2048`，并紧跟
3. 现在档位词那阶（第 ③ 步）直接写 `2560x1440` / `1440x2560` / `2048x2048`，并紧跟
   一句「和 2K 是同一档，因为本工具最大就到这里」。第十一轮又补上「横 / 竖 / 方」与三个
   数的对应——旧写法只给三个孤立的数，模型得自己猜哪个对哪个朝向。
   第二十二轮第三批把「回复里要说明出的是最大档、不是 4K」**收窄成条件句**：只有用户提的
   档位超出上限（说了「4K」「8K」「原图那么大」）才补这一句。旧写法挂在「用户提了 2K / 4K /
   高清时」上，于是只说了 2K 的用户也会被告知「出不了真 4K」——**元指令的触发条件必须窄到
   「用户真的问了那件事」**，宽一格就变成对所有人的噪音。

**「上限」只能用一组数说，而且必须是真上限。** 第 3 版残留一句「本工具的画布上限就到
`2048x2048`」，紧接着自己又给 `2560x1440`——**同段里 2560 就在那个「上限」之外**，
模型照字面转述「这是最大档」时说的是假话（`2560x1440` = 3,686,400，顶格的是
`2048x2048` = 4,194,304）。第十三轮改成「上限是单边 2560、面积 4,194,304（`2048x2048`
顶格），出不了 `3840x2160`」，并把 4K 写成「不设独立档，横竖方分别与 2K 同档，没说方向
就用方 `2048x2048`」。**一个上界只能有一种表述；两个约束（边长、面积）都要给的时候，
不能拿其中一个当「上限」的代称。**

**教训是「让工具兜底」不等于「故意走一条必然失败的路」**：兜底是为了让用户的怪尺寸
也能出图，不是为了把模型的错误藏起来。该说的实话（出不了 4K）仍然要说，只是这句话
从 `hint` 的副产物变成了描述里的硬要求。

**旧稿里「桌面横图 1536x1024」与「16:9 桌面 2560x1440」是两条互相打架的映射**（同一个
用途两个比例），子代理冷读时直接点了出来。现在拆成「横图 1536x1024」（3:2，通用横图）
与「桌面壁纸 2560x1440」两条，各自带明确比例，不再共用「桌面」这个词。第十一轮又往前
推了一步：比例词单列一阶之后，用途表里的括号比例全部删掉了——**「16:9」这类说法只在
比例词那一阶出现一次**，用途表只讲尺寸，否则同一个比例在两个地方各给一次，模型仍要
在两条出路之间选。

**「一次一张」写在第一句，但不写成否定句。** OpenAI 的 images 接口有 `n`，模型的
肌肉记忆会直接补一个 `n: 4`。早先的写法是「没有 n 这种张数参数」——对抗评审指出这句
是给模型脑中那个 OpenAI 式 API 打的补丁，白占字数且让整段读起来像「在防我」。现在第一句
正面说计量方式：「一次出一张，要几张就调用几次，每张都真实扣积分」。同理「`image` 是
改图的输入，写成数组」写在「可给多张参考图」**之前**（旧顺序先建立「多张才需要数组」的
暗示），并补一句「那是输出画布、不是原图尺寸」——否则模型会拿 `1024x1024` 去套一张
2.6:1 的条带，构图直接被重画。

> 这一条改了三轮才到位。第一版写「想保住原图构图就取接近原图比例的值」，子代理冷读
> 指出它要求模型知道原图尺寸，却没写**怎么知道**、也没写**不知道时用什么**；第二版改成
> 「拿不到原图宽高就用 `1024x1024` 并在 prompt 里写明保持原构图、不加黑边不裁切」，
> 又被指出几何上互斥（3:2 主体塞进 1:1 画布只能拉伸变形）。第三版干脆**不让模型回答这个
> 问题**：改图写 `size: "auto"`，宽高由工具从字节里量。**写行为指令时要给到「拿不到
> 信息时的兜底」，但更好的做法是让「拿不到」这件事不发生。**

> 同理，「只写数字和一个小写 x」与 schema 的 `^[0-9]+[xX×][0-9]+$` 曾经互相矛盾：
> 按正文写的模型不敢用 `1024X1536`，按 schema 写的模型写了 `1024×1536` 又要怀疑自己。
> 现在正文写「只写数字加一个 x（x / X / × 都认，会规整成小写）」，schema 的 pattern 也
> 放宽到 `^([0-9]+[xX×][0-9]+|auto)$`——**散文与 schema 的接受集合必须一致**，否则
> 模型无论信哪一边都有风险。

**描述本身讲用户关心的事，不讲防御条款。** 一段以「本工具只有这四个参数、没有 ratio /
return_base64」开头的描述，模型读完只知道不能做什么；用户问「这是国内版还是国际版」
「一张多少积分」「我要竖版壁纸」时它一条都答不上来。现在的顺序是四段问答 + 收尾：
(a) 画什么（prompt 怎么写、比例只由 `size` 决定）→ (b) 花多少 → (c) 走哪个区（含问价
怎么答）→ (d) **`size` 决策链与范围校验** → `image` → `model` → **计费边界** → 返回字段
（含 `hint` 与 `path` 的优先级）。黑名单式条款仍然保留在执行层（`rejectUnknownArgs`），
只在报错时说出全部合法参数。

**决策链要显式声明「按序命中即停」。** 第五轮对抗评审的原话：旧稿「先按下面四条选出
想用的尺寸」在字面上是**合取**（四条都要过），于是「4K 聊天配图」在一阶（给 2048 方档
但缺方向）与末阶（给 `1024x1024`）之间死锁，「改图 + 用户点名 2560x1440」在「照写」与
「改图同比例」之间打架。现在八阶前写死一句「按顺序匹配，命中一条就停」——
**并列的台阶默认会被读成「都要满足」，必须显式改成析取**。加台阶时要一起改这句
引导语：第十一轮插入比例词那阶时，引导语同步补了「比例词和方向词都算『用户提了』」，
否则「提了比例」算不算「提了尺寸」仍然要模型自己拿主意。第十二轮把原来的「用途/方向」
一阶拆成「用途」与「默认档」两阶，并在链尾补裁决句「用途和方向同时出现时按方向」——
**阶数变了就必须重读整条链有没有死锁**：拆阶是修复「横的配图被用途表吃成方图」，
但拆完必须保证每一阶都有出口，最后那一阶要能把所有剩余输入接住。

第十五轮又加了「表外比例」与「只提方向」两阶（第 6、第 7 步），同时把第 4 步里的方向
值挪进第 7 步、只留一句「见第 7 步」：**同一条规则只能有一份实体，其余地方写引用。**
旧稿把「只提了方向 → 横 `1536x1024`…」写在第 4 步（只对改图生效）里，于是文生图说
「来张竖图」时第 3 步的方向规则不触发（它挂在档位词条件下）、第 6 步又要求「也看不出
方向」，两阶都不命中——一半概率给出方图。方向上移到独立一阶之后，第 3 步定方向、
第 4 步的「只提了方向」、第 5 步的表外用途全部指向同一处。**引用悬空比写重复更危险：
重复最多是不一致，悬空是那一条请求根本没有出口。**

**算术交给工具，模型只负责说实话（第八轮的关键转向）。** 前七轮一直试图在描述里教会
模型「越界怎么缩」「改图怎么按比例挑档」。两个评审子代理各自实测出它做不到：
`2480x3508` 按长边缩成 `1810x2560`（边长合规，乘积 4,633,600 仍超上限）；改图时它
读不到本地文件、工具也不回传输入尺寸，只能猜。现在这两件事都下沉到执行层：

- 越界（含 4K 那种根本出不了的档位）→ `fitIntoRange()` 等比缩/放后**照常出图**，
  `hint` 里写明「按你给的 X 缩放成 WxH」，`requestedSize` 回带原值。**描述的义务从
  「教它算」变成「叫它别撒谎」**：那句缩放说明必须转告用户，不能把缩过的尺寸说成用户要的。
- 改图比例 → `size: "auto"`，工具从图片字节里解出第一张的宽高（PNG IHDR / JPEG SOF /
  GIF LSD / WEBP 三种子格式），按同比例给长边 1536 的画布（`1600x900` → `1536x864`）。
  只有比对 5:1 更细长、等比缩数学上无解时才退回方向常用档，并在 `hint` 里写「比例有变化」。

**本地只剩一种尺寸失败：比例极端到缩不出合法值。** 旧流水线是「校验 → 变换 → 不复查」：
`4096x512` 等比缩到长边 2560 得到 `2560x320`，短边仍 <512，必死在本地。现在
`fitIntoRange()` 里两个约束（边长 512–2560、总像素 ≤4,194,304）由同一个缩放比同时满足
——取「`2560/长边`」与「`√(4194304/面积)`」中更小的那个，floor 之后再用
`shrinkProduct()` 复查一轮（`2509x1673` 会差一点点越界）。缩完短边仍 <512 就试「抬到
512、另一边同比放大」，两边都无解才返回 `undefined`，由 `planImageSize()` 报
`INVALID_ARGS`（本地免费）。

**降级写成义务，而不是静默替换。** 用户给的具体像素一旦越界（`4096x4096`、`3000x2000`），
`fitIntoRange()` 会缩到合法范围内再出图——一次可能**像素掉好几倍**的降级。旧稿只写
「横的换 2560x1440」，配上「别反问用户」，模型只能闷头出图再报一句「尺寸已生成」。
现在描述里写明「hint 里那句缩放说明必须转告用户」；`auto` 遇到比 5:1 更细长的图被迫
改比例时同理（`hint` 里直接写「比例有变化」）。**降级可以，但要留痕。**

**费用放在第二段，而且要说清「不能选」。** 国内版约 5.71、国际版约 0.03，相差约 190 倍，
而 `additionalProperties: false` 让调用方**无法传 region、也无法探测**是哪个区。第五轮
冷读把这一点判为**报价死循环**：`region` 只在返回里、调用即扣费，等于先付费才能报价。
现在的写法是：先承认不可读（「调用前读不到、也不能由参数指定」），再给两条**可执行**
出路——① 用户问价就直接报两个区、**只用一个口径**（「每张：国内版约 5.71、国际版约
0.03 积分」，多张就按张数各乘一遍），不为问价出图；② 真要确切单价就必须真调一次，那就
**先把「这一次会真扣一次积分」说到、用户同意再调**，用返回的 `region` 与 `credit` 算出
真实单价，之后按那个数报。

> 第十八轮对抗评审把旧的三个报价口径并排贴出来打：同一段里同时写着「估价一律按国内版
> 5.71 说」「报两档 + 190 倍差距」「没给 `credit` 就按这两档估」。**同一件事有三种说法，
> 模型每次只会执行其中一种**——于是同一张图可能报 5.71，也可能报「国内 22.8 / 国际
> 0.12」还漏了单位（前面的「积分不等于人民币」又把读者往「元」引）。现在只留一个句式：
> 两个区各一个数；**本次调用**（同一张图、同一次请求）拿到过 `credit` 的才按那个数报，
> 不再报两档——第十九轮冷读指出旧句「已经拿到过」没限时间，模型会把上一次的单价搬到这一次，
> 而 190 倍差正是跨区、跨模型产生的。**报价不是估算，是复述：能复述的只有这一次的
> `credit` 和写死的这两档。代价不可控时，描述的义务是让模型把不确定性讲给用户听，
> 而不是装作能选、也不是让它先偷偷花一次钱。**

> 早先这里写的是「先出 `512x512` 一张小的探一次」——被自己推翻了：尺寸与单价的关系
> 没有实测（`tests/` 里没有任何一条断言证明小图更便宜），而描述里写一句没验证过的
> 定价规律，等于把一个猜测固化成模型的行为。改成「先征得同意出 1 张」不需要任何定价
> 假设，代价也是确定的。
>
> 第十九轮又把「多版」的同意卡与「多张」的同意卡合并成同一张：旧稿的开头写「先把张数和
> 总价说出来，用户同意再连着调」，紧接着又写「要『多版挑一张』就先出 1 张」——用户批的是
> 4 张的预算，拿到的是 1 张，模型要么违背承诺跑 4 张、要么收了 4 张的授权只交 1 张。
> 现在只有一个说法：「先出 1 张给你看，满意再按张补后面的，每张单独计费」。**同一件事在
> 同一段里只能有一张同意卡；两张卡就是两个付款口径。**
>
> 第二十二轮对抗评审又指出：合并成一句之后，这句话本身变成了一条「正向可执行指令」，
> 而它前面那句「一次调用只出一张图，要几张就调几次」更早、更顺、也更能执行——于是
> 「照这张来 4 张同款」会被字面执行成 4 次调用、4 次扣费，买到的却是 4 张互不相同的图
> （描述里还预先写了「同一 prompt 重调不保证张张一样」，等于自己给自己免责）。
> 现在把「多张」写成**三态**，判据只有一条——用户要的是「一样」还是「不同」：
> 说「一样/同款/同一张/复制几张」→ 直接说做不到，让他出一张自己复制，**不报价也不调用**；
> 说「不同风格/各来一张」→ 报张数与总价、等明确同意、连着调 N 次、每次换 prompt；
> 说「挑一张/先看一张」→ 先出 1 张，满意再按张补、补之前重新报一次总价。
> **正向指令比否定补丁更容易被字面执行**：把所有「别把这条套到……」的补丁换成一个
> 先判「一样还是不同」的分支，才不是靠读者记得往回读。

**开关关掉要给处置，不只给错误码。** 「走哪个区」的判据之一是「有没有开允许模型自主
生图」，但旧稿只说这是判据，没说没开时会怎样。现在写明会报 `NOT_LOGGED_IN`，并要求
「让用户去插件设置里把两个区都查一遍：登录了没、那个开关开了没」。第九轮对抗评审指出
这个错误码**一码两病因**（没登录 / 没开开关），只说「去设置里看看」模型会把两件事混成
一件；把两件事都列出来，用户才知道该点哪一个。第十八轮冷读又指出：错误载荷里
**没有** `region` 字段，而描述让模型说「这个区」——模型说得出口，用户看不出是哪一个。
现在改成「把两个区都查一遍」，不再要求模型知道是哪个区。**一个不可自愈的失败，描述必须给出
下一步动作**，否则模型只会重试三次。第十二轮又补半句「报这个错时还没发请求，不扣
积分」——它同时出现在计费边界段的「本地就拒」清单里，两处必须说同一件事，否则模型
读前半句以为要赔钱、读后半句以为可以随便重试。

**「开关」是准入门槛，不是选区判据。** 第十二轮冷读按字面读出两个互斥的读法：把
「有没有打开允许模型自主生图」当成决定走哪个区的因素，会以为「关了开关就换区」；
而实现里 `imageToolRegionOf()`（`src/index.ts:1317-1323`）要求 `regionEnabled` 与
`imageToolEnabled` **同时**成立才把这个区算进候选，一个区都不满足就根本不注册工具。
现在描述写成「本次走的是『开着且打开了那个开关』的区」，把门槛与顺序分开：先要
有资格，再谈优先（`REGION_KEYS` 的顺序让 `cn` 在前，两个区都满足时走国内版）。
同一段还补了 `cn=国内版、global=国际版` 的映射——正文一直叫「国内版」「国际版」，
返回值却是 `cn`/`global`，中间没有一句翻译，模型会原样把 `cn` 说给用户听。

**计费边界单独成句。** 早先只写了「越界会在本地被拒绝、不扣积分」——失败×计费的矩阵
只有一格。对抗评审的原话：model id 填错、图 >8 MB、内容审核、上游 5xx 是否扣费全空白。
现在写清两组：本地就拒的（`size` 不是「宽x高」也不是 `auto` / 比例
极端到缩不进范围 / `image` 空数组 / model 不存在 / 图读不出来 / 图超 8 MB /
`NOT_LOGGED_IN`）**确定不扣积分**；已发到上游的（超时、审核拒绝、上游报错）**可能已扣费**。

> 第十四轮从这份清单里删掉了「数字小到画不出来」。它和同一段上面的「越界不用你换算，
> 工具会等比缩/放后照常出图」是**对同一个 `300x300` 的两种钱的说法**：实现里
> `fitIntoRange()` 遇到最短边 < `MIN_IMAGE_EDGE` 时会按 `512/shortest` 放大
> （`src/image-tool.ts:581-585`），根本不报错。清单里每一条都要能在代码里指出抛错点，
> 否则它就是在拿用户的积分说一件不会发生的事。

第十二轮把判据又收了一次口：旧句「成功一定会返回 `url`，抛错就说明这一次没拿到图」在
字面上与「超时也可能已扣费」互斥——「没拿到图」被读成「没花钱」，于是模型会让用户再花
一次。第十三轮的两个盲读子代理各自又指出首句「成功出一张才扣一次积分」是**绝对句**
（没成功＝不扣），与「超时可能已扣费」还是对撞。现在的写法是**把扣费拆成三种说法，每种
只讲一种情形**：

- 返回带 `url` 又带 `credit` → 按 `credit` 说实扣了多少；
- 带 `url` 但没 `credit` → 按 (b) 的两档估，并说明以账单为准；
- 没拿到图、但请求已经发到上游 → 只能说「这一次没拿到图、可能已扣费」，不得断言没扣费、
  不得自己重发。

**「约」价与实扣对不上时要照实说。** 5.71 与 0.03 是两个区的目录价，真正的结算数只有返回里的
`credit`。第二十轮冷读的 C8 指出的正是这里：旧稿只在「返回带 `credit`」时按 `credit` 报，
没有规定「报出去的是 5.71、回来却是 0.03」时怎么办——模型会顺手说一句「约 5.71」，把一个
差了 190 倍的事实圆过去。现在描述里写「实扣和你报的『约』对不上（差一个量级通常说明这次走了
另一个区）就照实说实际扣了多少，别替它圆」。**估计值必须自带一条「估计错了怎么办」，
否则它会在出错时被当成结论。**

**重试也是一次要重新授权的计费决策。** 早先只写了「本地拒的那种可以改完直接重试」，其余情形
沉默——模型于是把「没拿到图」当成「没扣钱」，同一条 prompt 连发几次。现在补一句「重试等于新的
一次计费决策：本地拒那种改完直接重试；其余情况重试前按 (b) 重新报价并取得同意」。判据挂在错误
码上（`INVALID_ARGS` / `NOT_LOGGED_IN` 是本地拒），不挂在模型对「这次到底扣没扣」的判断上——
**能判定的事交给代码，判不了的事才有资格交给叙事。**

**确定的事用肯定句，不确定的事交给用户——中间不留一句既可以读成 A 也可以读成 B 的话。
绝对句（「才扣」）和例外句（「也可能扣」）不能分居两段，否则被复述的永远是那句绝对句。**

**`size` 的规则收敛成一条优先级链，不再并列若干「默认值」。** 早先的描述同时写着
「用户没说尺寸就按用途自己定一个」与（改图段的）「不知道原图就用 `1024x1024`」，两条
在「给了图但没给尺寸」时互相打架——一次出 `1536x1024`、一次出 `1024x1024`，同一需求
两次调用尺寸不同。现在只有一个入口、八个按顺序命中的台阶（命中一条就停）：

1. 用户**对输出图**给了具体像素 → 先规整成「数字 + 小写 x」再传（`1024*1024`、
   `1024 × 1024`、`1024 by 1024` 都写成 `1024x1024`），越界由工具缩（见上）。**规整必须由
   模型完成**：schema 的 `pattern` 只收「数字 + `x`/`X`/`×`」，带空格、`*`、`by` 的值会被
   宿主直接拒掉，工具那层的规整发生在参数进来之后——第十七轮冷读把它读成了「工具会替我
   规整」；
   改图时用户说「我这张图是 1600x900」是在交代**输入图**，不算提了输出尺寸。第二十轮曾让
   排除句「自带去向」（写成「落到第 4 步那条……写 `auto`」），第二十一轮又发现**去向写在第 1 步
   也在犯错**：`1600x900` 字面上就是「数字 + x」，第 1 步的触发词（用户给了具体像素）会先把它
   吃掉，脚注里的「写 `auto`」只能事后纠正。现在措辞改成**只留否命题**——「输入图的宽高永远
   不是 `size` 的值……照第 4 步处理」——把分类这件事整个搬到第 4 步的首句去做（见下面那段
   「第 4 阶要先分类，再派发」）。**排除句不只要给去处，还得保证自己不会被同一句的触发词先吃掉。**
     第二十二轮对抗评审又指出：这句里"都写成 `1024x1024`……带空格、`*`、`by` 的写法宿主会直接
     拒掉，改写必须你自己做（大小写不用管，`X`、`×` 工具会替你规整成小写）"共 100+ 字，是在用
     自然语言复述一个正则；而且"大小写不用管"与 `pattern` 里的 `auto` 分支并不一致。现在压成
     「都写成 `1024x1024`；带空格、`*`、`by` 的写法宿主会直接拒掉，改写必须你自己做；大小写和
     `×` 不用管」。**schema 已经强制的事不要用自然语言再抄一遍**——抄了就要维护两份，
     而两份迟早不一致。
2. 用户说的是**比例词**（16:9 / 9:16 / 4:3 / 3:4 / 3:2 / 2:3 / 1:1）→ 一词一档，值是
   定死的，所以「2K 的 16:9 壁纸」仍是 `2560x1440`、不因为又说了 2K 就变成方图；比例词压过
   档位词与形状词（「16:9 横图」也是 16:9，不是 3:2）。唯一例外是「1:1 + 2K/4K/大图」→
   `2048x2048`。**别写「各档都已顶到上限」**：`3:2` 是 `1536x1024`（1.57M），离 4,194,304
   还差得远，同段又写着「上限两条边各 512–2560」——两句话读起来像在说「上限是 1536」。
   档位值是**定死的**，不是「顶格的」；
3. 用户说的是**档位词**（2K / 4K / 高清 / 1080P / 720P）→ **只在没提比例词时**生效，
   换成本节列出的标准像素（4K 不设独立档，横竖方与 2K 同档）。**每个档位词都要给横竖两个值**：
   第十七轮冷读追问「1080P 手机壁纸」，而 `1080P` 只写了 `1920x1080`，同阶又说「用途只用来
   定方向」，字面无解——只能落横图，与「手机壁纸算竖」正面冲突；现在写成「`1080P` 横
   `1920x1080`、竖 `1080x1920`」，「`720P`」同理。
   **方向只能有一套默认。** 第十九轮之前的这一段里同时住着两句反向默认——「`1080P` 看不出
   方向就按横的写」与「用途也没说就用方」——同一段话对「`1080P` 的头像」给出两个答案。
   现在收成一句总则「用户明说 → 看用途 → 按方」，再单独给无方档的两个词一句例外
   （落到「用途也没说」时按横，并说明竖版要按用途定）。**例子也不能撞词**：原来这一阶用
   「`1080P` 的头像」当竖版例，而第 5 步的用途表把「头像」放在**方行**——同一个词在同一份
   文档里两个方向。第二十一轮换成「`1080P` 的竖版海报」（这一行在第 5 步本来就是竖的）；
    第二十二轮又把这一阶里的**元指令**删了：旧稿要求模型在回复里固定说一句"按横版给的"，
    而这句话对用户没有任何作用，只是一条替描述自我解释的话术；同时把"所以它们那条『用途也没说
    就用方』不适用"压成"这两个落到『用途也没说』时按横的给"。**为已经说清的值再写一条二阶
    例外，是把上下文税当成了严谨。**
4. 有输入图（改图）→ **先在「输出尺寸」和「输入图尺寸」上分一次类**：「改成 `1200x800`」
   「要 9:16」是输出；「我这张是 1600x900」是输入，输入尺寸永远不填进 `size`，这种情况直接
   写 `auto`。分完类才进派发：提了输出像素 → 用第 1 步；提了比例 → 用第 2 步；提了档位词 →
   用第 3 步；提了用途 → 用第 5 步；
   **只提了方向** → 用第 7 步；只说了「保持原比例」「版式别动」或什么都没提 → 写 `auto`，
   工具自己量。改图时 `size` 的比例与第一张输入图不同，工具按 `size` 裁切或留白——**这句要
   在调用前说**：「会按这个比例裁切/留白，原版式可能被切」，用户同意再调；见下面那条
   「改图裁切不能等出完图再说」；
    **同一句里既有输入图尺寸又有比例时，输入那个数不参与匹配。** 第二十二轮第三批的对抗评审
    逐字推演「这张 4000x1000 的图改成 4:5」：按派发顺序第 1 步先命中（4000x1000 也是「数字 +
    x」），填进去被工具缩成 `2560x640`（4:1 横），与用户要的 4:5 方向相反、还照扣积分。现在
    明写「4000x1000 只是输入尺寸，size 填第 6 步算出来的 4:5 那组」——**排序解决不了「同一个
    字符串属于谁」的问题，只有分类能**。
5. 用户说了**用途**（配图 / 插图 / 封面 / 头像 / 表情包 / 大图 / 桌面壁纸 / 手机壁纸 /
   竖版海报 / 手机开屏）→ 表里每行自带方向，命中一行就用它；**用户另外说的方向与这一行冲突就
   交换宽高**（横的行他要竖 → `1024x1536`；竖的行他要横 → `1536x1024`；方的行他要横 →
   `1536x1024`、要竖 → `1024x1536`），方向相同就照这一行走（「做张手机壁纸，要竖的」仍是
   `1440x2560`）。比例词已命中的到不了这一步（「1:1 的配图，要横的」按第 2 步走）。
   **第十九轮补的是「方行遇方向」这个缺口**：旧稿只写「横行要竖」「竖行要横」，配图行是方行，
   「给这篇文章配张图，要横的」于是无定义，模型照「命中即停」填 `1024x1024`，与同一段自带的
   例子 `1536x1024` 打架。第二十二轮又把三支枚举收成一句「冲突就交换宽高」——**枚举漏掉的
   第四种情形是「方向与这一行相同」**（「做张手机壁纸，要竖的」），而它恰恰是最常见的一种。
   用途不在表里 → 用第 7 步；
    **「竖版」「横版」「方图」单独出现是方向词，走第 7 步，不算用途**（第二十二轮第三批），
    用途行里的「竖版海报」要说到「海报」才算命中。旧写法两处都收，用户说「把这张改成竖版」时
    「竖版」既是方向词（`1024x1536`）又与表内「竖版海报」同形（`1440x2560`），裁切幅度差 40%。
    **同一个词只能在一阶里有身份**，另一次出现必须带足限定词。
6. 用户说的是**表里没有的比例**（4:5 / 21:9 / 5:4 …）→ 按该比例直接算一组像素：
   **两个上限取更严的那个**（长边 2560、面积 4,194,304），按比例算完取整、再把宽高乘一遍验算
   （`21:9` → `2560x1097`；`4:5` → `1831x2289`，再多一号就超面积），并说明实际出的
   比例。**例子必须能被算法复核**：旧例子写 `4:5 → 1600x2000`，长边既不是「尽量 2560」、
   面积也只有 3.2M（上限 4.19M），凭空少了约 30% 像素——第十七轮对抗评审照着自己算得
   `1832x2290`，与例子对不上，等于同一份文档给出两个答案；
7. **只提了方向**（横 / 竖 / 方），比例、档位、用途都没提 → 横 `1536x1024`、竖
   `1024x1536`、方 `1024x1024`。这一阶管所有方向词：第 4 步的「只提了方向」、第 3 步的
   方向三级、第 5 步的表外用途，全部落到这里；
8. 以上都没命中、也看不出方向 → `1024x1024`（默认档），并说明这是默认档。**这一阶只定
   尺寸，不定主体**：第十七轮两个子代理都卡在「来张竖图」上——(a) 说「主体没给先问『想画
   什么』」，第 8 步又说「都没命中给默认档」，同一情形两读法；现在第 8 步显式限定「只定
   尺寸」，主体缺失仍走 (a)。

**「什么时候必须先问」只能有一份清单。** 第二十轮为了堵「每出一张图都先请示」，写了一句
「单张不必为『要不要花一次积分』单独请示（用户让你画就是授权）」——两个盲读子代理都把它
判成全文最危险的一句：它把授权扩张到「不等裁切确认也能扣费」，与同段「改图比例变了要先说、
他同意再调」正面冲突，而「并成一次确认说完」又引入第三条阈值。第二十一轮收成一份五条清单：
**要出超过一张、会改变原图版式、要真调一次才能报价、主体还没定、用户要的东西本工具做不到**
（真 4K、硬性排除某个元素），命中两条以上合成一次问完，五条都不成立才直接调。
**「不必请示」是授权扩张，它必须被一条可判定的清单取代，而不是被一句更宽的话取代。**
第二十二轮对抗评审逐字推演出两个新口子：① 第三条原来是「要真调一次才能报价」——可 (b) 已经
要求「没拿到 credit 就报两档」，两档价永远报得出，这一条于是永不成立却给了「花一次钱问价」
的许可，与 (c) 的「说清会真扣一次、用户同意再调」形成两套触发条件；现在改成**可判定**的
「用户要确切的、能写进预算的单价（两档价不够用）」。② 「用户**刚**说嫌贵」里的「刚」没有
界——上一轮喊贵、这一轮画猫，字面判成「不是刚」就直接调、按国内版扣 5.71；现在写成
**「本轮或上一轮里说过嫌贵」**。**停等条件必须可判定，否则它只会被跳过。**

**清单要能列出「所有」停点，否则「只看这 N 条」是假命题。** 第二十二轮对抗评审把这份清单
逐条对着工具描述跑了一遍，抓到两个缺口和一处自相矛盾：① 提示词压缩那条写着「压到 300 字以内，
把那版发给他看一眼、他说行再调」——这是清单之外的第七个停点，而正文宣称「只看这七条」；
② 「用户要的东西本工具做不到（**真 4K**、硬性排除某个元素）」与第 3 阶「4K 不设独立档、
照 2K 填、回复里说明实际档位」正面对撞：同一句「来张 4K 壁纸」，照第五条要先停、照第 3 阶
要先调完再解释，字面执行必违反其一。现在 ① 改成「压完直接调，并在回复里附上实际用的那版
prompt」——**压缩是可逆的信息损失，不是一次授权**；② 改成「明确要 `3840x2160` 这类超过 2560
的像素」——**只有用户指名了工具出不了的像素才是真正的「做不到」；档位词是用户的说法，不是
他的诉求**。清单同时补齐到七条（新增「要自己按表外比例算像素」「本轮或上一轮说过嫌贵 / 正要改
区设置」）。

**「告知」只覆盖价格，不覆盖任何会被写进图里的东西。** (b) 原来写「单张也要先说价再调，这是
告知、不用等同意」，而第 4 阶写「改图比例变了要先说、他同意再调」——用户只说「改成 9:16」时，
两条规则同时命中，一条说直接调、一条说等同意，模型挑哪条都说得通。裁切不可逆、价格可逆
（多花一次 vs 版式被切坏），所以现在 (b) 的告知句后面直接挂一个例外：**「改图会改版式、要出
多张这些仍在七条里，得等同意」**——一句话里把「告知」和「请示」的边界钉在同一个句号内，
不留缝给第二种读法。

**「只说张数、没说同异」必须有个分支。** 旧稿的多张判定只有三条：「一样」→ 做不到、「不同」→
报价、「挑一张」→ 先出 1 张。用户问「4 张要多少钱」时三条都不命中：报价等于对一件可能做不到
的事报价，不报又违反 (b) 的报价义务。现在补第 0 条：**先问「要一样的还是各不相同的」**，再按答案分流。**问价请求本身就是一次需求澄清，它不该被当成「已经说清了需求」来处理。**

第二十二轮第三批把这条推到根上：**问题不在少了第 0 条，而在这三条写在「要超过一张时先判」
这道门里。** 用户说「上次那张再画一遍，要一样」只要 1 张，门不成立，于是落到「直接调」——
同一个请求，走 (i) 是 0 次扣费、走门外的兜底是 1 次扣费，两条都逐字可读。现在把三条提到门
外，写成「跟要几张无关——用户要的是『一样』还是『不同』」，并把「本工具没有 seed、不存历史、
不能重放」提为**全局事实**（它本来就不是条件句，却被写在分支里当理由）。**条件门只能圈住它
自己那一条分支**：一条绝对禁令写在「>1 张」的门内，单张那条路就没被它管住，而读者会以为管
住了——作用域写错比写漏更难发现，因为两处都「有字」。

**同一个动作只能有一套台词。** 改图只换尺寸时，(a) 一处让 prompt 写「保持主体、细节和光线
不变，只换画布」，另一处让只写「保持主体和光线不变」；两句都对「改方向 + 换比例」生效，而
「只换画布」在事实层就是错的——工具做的是裁切/留白，画布变了、画面也变了。这已经不是措辞
问题，是其中一句在让模型对用户撒谎。现在统一成「别写『构图不变』也别写『只换画布』，只写
『保持主体和光线不变』」，只说改尺寸时给范本「保持主体和光线不变，按新的画布重新构图」。
**台词冲突时要按事实判定谁对，不能挑一句留下。**

**枚举分支要写成「冲突时怎么改」，不要写成「每种组合各给一个值」。** 第 5 阶原来把用途表 ×
方向词展开成三支（横行要竖、竖行要横、方行要横/要竖），三支之外还有「方向与这一行相同」这种
第四种情形没写——「做张手机壁纸，要竖的」字面找不到出口。现在收成一句：「方向与这一行冲突就
交换宽高，相同就照这一行走」。**分支的数量应该等于「需要做出不同决定」的数量，不是「组合的
数量」。**

**第 4 阶要先分类，再派发。** 旧稿的 ④ 第一句就是「按这个顺序定：提了输出像素 → 用 ①」，
而 ① 的触发词是「用户对输出图给了具体像素」——用户说「我这张是 1600x900」时，字面上
`1600x900` 就是「数字 + x」，先命中 ①；① 的脚注又说这属于交代输入图、该写 `auto`。**主句和
脚注在同一阶给了两个答案，而正确的比例词那一阶排在它们后面。** 现在 ④ 的第一句是分类：
「改成 1200x800」「要 9:16」是输出；「我这张是 1600x900」是输入，输入尺寸永远不填进 `size`。
分完类才进派发表。**排除与派发不能住在同一阶的同一句里**——排除句会被主句的触发词先吃掉。

**例子的正反两面不能在同一个词上。** (a) 原来举例「秋季新品静物」算主体，紧接着又说「只说
『主题』不算给了主体」，而用户原话「做张竖版海报，秋季新品」正好卡在这两个例子的中间——
一个例子说算、一个定义说不算，逐字执行者只能掷硬币：要么白问一句，要么替用户编货品并扣费。
现在两个例子换成不同的词（「一束向日葵」是主体、「秋季新品」是主题）。**举例也算规则**：
同一个词不能既当正例又当反例。
**链的入口还有一道门禁：主体没定，整条链都不许走。** 第十九轮把 (a) 的「主体没给就先问」
提到链首之前，(a) 与第 8 阶是并列的两句规则：用户说「随便画个 `16:9` 的」时，一边让他先问
「想画什么」，另一边第 2 阶已经命中 `2560x1440`——模型照后者直接自编一个主体扣一次费。
现在链的引导句是「**先过 (a) 的主体门槛**：主体没给、还在问『想画什么』的时候，后面的推导
一条都不要走，更不要为了尺寸先出一张」。**互相矛盾的两条规则，光各写清楚不够，还得写明谁
先谁后**；顺序不写，等于两条都生效。
第十二轮把原来的第 ⑤ 步拆成「用途」与「默认档」两阶，并补一条链尾裁决句「用途和
方向同时出现时按方向」。第十三轮又把这条裁决句删了——**它自己造了一个双解**：追问
「做张手机壁纸，横着看的那种」时，用途表给 `1440x2560`（竖），裁决句又指向
`1536x1024`（横），两条都是「按文本执行」，模型只能猜。现在的写法是把方向并进用途表
本身（每行自带方向，命中一行就用它、不再降级），方向只在**表里的行与用户另外明说的
方向不符**时才出手：「要竖的改 `1024x1536`，要横的改 `1536x1024`（『给这篇文章配张图，
要横的』→ `1536x1024`，不是 `1024x1024`）」。**同一条链里不能有一个「总纲」和一张
「表」各答一次同一个问题——要么表里带方向，要么总纲说了算，不能两样都在。**

**同一个词不能在两阶上有两种身份。** 第二十轮冷读把「大图」拎出来：第 2 阶里它是
「不触发升级」的修饰词（「1:1 高清 / 大图才写 `2048x2048`」），第 5 阶里它又成了用途行
（「方图大图 `2048x2048`」）——用户只说「画张大图」时两阶都不命中，落第 8 阶的 `1024x1024`，
而「大图」在中文里明显是要大的。现在第 5 阶把它写成「要『大一点的方图』或『大图』**单独出现**
→ `2048x2048`」，第 2 阶只在「已经命中某个比例词」时把它当修饰词。**一个词只有一阶能给它定义，
别的地方只能引用那一阶。**

**第 6 阶（表外比例）必须自己排除 5:1 那条死路。** 旧稿让模型「按比例自己算一组像素」，
范围段又说「比 5:1 还细长就在本地报错、不扣积分」——两句都对，合起来是「先算出
`2560x320` 承诺给用户，然后必然被本地拒」。现在第 6 阶末尾自己写「算出来的比例不能比
5:1 更细长……遇到这种比例改用 `auto`，或先跟用户说最细只能到 5:1」。**凡是有一阶会产出
「另一段明确禁止的值」，那一阶就得自己带上这条限制**——限制写在别处，等于没写。
**比例词必须单列一阶，不能让它靠用途表兜。** 第十轮冷读把它排成第一条要害：轮到
「照着这张 1600x900 的图改成 9:16」时，`9:16` 既不是具体像素、也不在档位词枚举里，
整句话唯一提到 `9:16` 的地方是用途表里的「手机壁纸」，而那句话要求用途命中——于是
这条请求被第 ④ 步的 `auto` 吃掉，输出仍是横图，而且不报错。比例词是用户最直接、
也最常说的诉求（封面 16:9、海报 3:4、头像 1:1），必须在链上有一个自己的位置。

**比例词一阶里也只有一个答案，不许出现「或」。** 第十一轮这一阶写的是「`9:16` 
`1440x2560` 或 `1024x1536` 按长边需求选」——两个候选里后者是 2:3，被标成 `9:16` 的
选项，模型挑它就等于对用户说谎；而「长边需求」这个判据在描述里从未定义。第十二轮
删掉二选一，改成「一词一档」，并补 `3:2`/`2:3` 两格（旧表里 `1536x1024` 明明是 3:2，
却从来没有被标注为 3:2，用户说「3:2」时无处可查）。**同一阶里出现两个候选，等于把
选择权退回给模型——而模型手上没有任何判据。**

**第 ④ 步从「看横竖」升级成「写 auto」。** 旧稿要求模型自己判断输入图是横是竖是方，
并按比例挑最近的常用档。冷读子代理指出工具**不返回输入尺寸、也没有 preflight**
（返回的 `size` 是输出画布），本地路径的图必须自己开文件读像素——把一个自己没提供的
能力写成必须步骤；而且「最近档」没有度量（16:10 该算接近 3:2 还是 16:9？），两个模型
会给两个答案。现在第 ④ 步只要求写 `auto`，宽高由 `parseImageDimensions()` 从字节里
解（PNG / JPEG / GIF / WEBP），按同比例给长边 1536 的画布。**模型看不到的东西，不要让
它猜；能自己量的，就不要写进描述。**

> 删掉的还有「拿不到原图宽高就用 `1024x1024` 并在 prompt 里写明保持原构图、不加黑边
> 不裁切」：3:2 主体塞进 1:1 画布，「保持原构图 + 方画布 + 不裁切 + 不加黑边」四者
> 互斥，唯一出路是拉伸变形，而拉伸恰好破坏「保持原构图」。这条 prompt 在几何上无法
> 满足，等于让模型写一句自己知道做不到的话。**能执行的兜底才算兜底。**

**「套用最近档」不是一条能算出这个比例的规则。** 第十五轮给表外比例（4:5 / 21:9 / 5:4）
开了一阶，但写的是「按该比例的方向套第 7 步的档位」。第 7 步只有三个固定值
（`1536x1024` / `1024x1536` / `1024x1024`），套出来的永远是 3:2 / 2:3 / 1:1——用户要
4:5，拿到的是一张 2:3，而「按最接近的常用档出图」只是事后免责，不是换算。两个盲读
子代理各自独立点名这条「规则本身无法成立」（−1.5 分）。第十六轮改成按比例直接算像素：
长边尽量取 2560，面积不能超 4,194,304，超了把长边往下取、另一边按比例算完取整
（`21:9` → `2560x1097`；`4:5` 取 `2048x2560` 会超上限，缩到 `1831x2289`），回复里写明
实际比例。**例子还要能被算法复核**：第十六轮的 `4:5 → 1600x2000` 长边既不是「尽量
2560」、面积也只有 3.2M（上限 4.19M），第十七轮对抗评审照着自己算出 `1832x2290`，与
例子差 30%——同一段文字给出两个答案，比没给答案更糟。**「取最近的一档」只有在档位格子里本来就有这一档时才成立；格子里没有，就得
给算式，不能给一个听起来像算式的说法。**

**改图裁切不能等出完图再说。** 同一轮之前第 4 步写的是「工具按 `size` 裁切或留白——
这种情况要告知用户，并问要不要改用 `auto`」。「这种情况」什么时候成立，要靠比较
输入图比例与 `size` 比例；模型在调用前既拿不到输入图宽高、也没有 preflight，照字面
只能先出图、再问——用户被扣了一次费，还可能拿到一张缺角的图。第十六轮改成调用**前**
说：「会按这个比例裁切/留白，原版式可能被切」，用户同意再调；不接受就改用 `auto`。
**任何「事后问用户要不要换做法」的义务，只要判断依据在调用前拿不到，就会变成一次已扣费
的试探。要么把判断挪到调用前能做的位置，要么把问题挪到调用前问。**

第十七轮补了两个缺口：**① 义务不能只挂在「写了具体比例」那一支上。** 「只提了方向」同样
换画布（`1536x1024` 之于一张竖图就是把上下切掉），但第 4 步的裁切预警原来只对「写了具体
比例」生效，于是「把这张改成横的」会静默改版式。现在写成「只要 `size` 的比例可能和原图
不一样（写了具体比例，或按方向 / 用途给了某个档）」，把三支都收进来。**② 改图的 prompt
范本与裁切事实互斥。** (a) 要求用相对说法「保持第一张图的主体、构图、光线不变」，可这次
`size` 换了比例时恰恰保不住构图——两句话在同一个请求里打架。现在补一句「这次 `size` 换了
比例时别写『构图不变』，只写『保持主体和光线不变』」。**义务扩大到哪里，范本就要缩到哪里；
否则模型会把一句自己知道做不到的话写进 prompt。**

**同一条链里不能有两处回答同一个问题。** 旧稿的 2K 只给横/竖两格（竖的还写成 9:16），
与用途兜底里的「竖图 2:3」打架；4K 的三向降级值与 2K 完全重合，两档塌成一档。现在 2K
给横/竖/方三格，4K 直接给本工具的最大档（`2560x1440` / `1440x2560` / `2048x2048`）
并明说「出不了真 4K」——**同一件事只有一个出口，不靠两个入口各说一半。**

第十四轮发现这条规矩只落到「值」上，没落到**辖域**上：第 2 步与第 3 步都能回答「2K 的
16:9 壁纸」（前者给 `2560x1440`，后者给 2K 方图 `2048x2048`），而第 2 步里那句「（用户
同时说了 2K / 4K / 大图时才用 `2048x2048`）」只挂在 `1:1` 后面，**括号辖域看不出来**——
照字面读整句都可被 2K 覆盖，于是模型给出一张方图当壁纸，还已经扣了费。现在第 2 步明写
「比例词压过档位词和形状词」并给出这个反例，第 3 步明写「只在用户没提比例词时生效」。
同一轮里「2K / 4K 的披露义务」也从第 3 步搬到了整条链的总纲（「用户提了 2K / 4K / 高清时，
不管最后命中哪一阶」）——原来它挂在第 3 步里，一旦请求命中第 2 步（如「4K 16:9」），
那句「不是真 4K」就整句丢失。**义务要挂在链上，不要挂在某一阶上；挂在阶上，绕过那一阶
就等于绕过义务。**

**走 `auto` 的那一步只在「用户没提比例、也没提方向」时生效。** 第九轮冷读发现一个
残留漏洞：用户说「把这张改成 2K」，按顺序会先命中档位词那一阶（换成 `2560x1440`），
于是原本为了「保住原版式」才写的 `auto` 反而被绕过——降了档却改了比例。第十一轮又在
它前面插了比例词一阶，边界变成三段：具体像素 / 比例词 / 档位词都算「用户提了」，
都不提才轮到 `auto`。`auto` 那一阶自己也写明「用户说『保持原比例』『版式别动』也走
这一条」，堵住「改图方图 + 保持比例出个 2K」这类反例。

第十四轮把这一阶从「补丁段」改成一条**有序派发**：提了比例 → 第 2 步；提了用途 → 第 5 步；
只提了方向 → 第 7 步（第十五轮把值从这一阶搬走，这里只留引用）；只说「保持原比例」
或什么都没提 → `auto`。旧稿的写法是「没提比例也没提方向 → auto」后面再补一句
「提了方向就按方向给档，不要用 auto」，**但没给具体值**——「把这张改成横的」照样只能猜，
而且那半句带着「别再被『版式别动』拽回 auto」这种跟自己的历史 bug 对话的措辞。
`auto` 本身又是**条件式**的（条件不成立时它不该出现），把它排在一串无条件分支后面，
读者要先做一次布尔判断才能确定轮不轮得到它。**分支要写成派发，不要写成「默认 + 例外」。**

**「纯文生图要省掉 `image` 字段」必须显式写出来。** 只写「`image` 永远是数组」时，
模型会把它读成「每次都得给这个字段」，于是补一个 `image: []` 撞上 `minItems: 1`
直接校验失败；而且「永远是数组」与「不给就是文生图」在字面上互斥。执行层也不再宽容
空数组（早先 `asImageList` 把 `[]` 当「没给图」返回 `undefined`，等于把「想改图但图
丢了」静默降级成文生图，照扣积分）：现在 `[]` 报 `INVALID_ARGS`，文案直接给出
「纯文生图请把 image 字段整个省略」。

**参数说明里已经写清的事，正文不要抄第二遍；但正文不能假装那些能力不存在。**
`image` 的五种入参形态（本地绝对路径 / `file://` / `http(s)` / data URL / 裸 base64）
与 8 MB 上限原来只在 `parameters` 里，正文一个字没提——第五轮对抗评审把它列为「最像
漏写」的一条，第七轮于是在正文抄了一份。第十六轮又删回指针（「格式与 8 MB 上限见
`image` 参数的说明」）：同一段文字在工具定义里出现两次，改一处就漂一处，而这次两个
盲读子代理都把重复本身列进了「最该删的三句」。`hint` 与 `path` 则是另一回事——它们只
出现在 output schema 里、正文从没解释过，所以必须留在正文（`path` 何时出现不清楚时，
「24 小时失效」这条建议对本地文件并不成立）。**判据：能力/形态/上限只写一次，写在离
参数最近的地方；会改变回复措辞的事实（`hint` 可转述、`path` 不过期）写在正文。**

**批量的唯一硬规矩是「一次一张」，不是「每次都换 prompt」。** 早先写成「要几张就调用
几次，每次换 prompt——换姿态、视角、光位」，对「同一张出 4 版让我挑一张」这种再正常
不过的需求是错的（照字面必须换 prompt，等于放弃同题对比还多花 3 份钱）。现在首句写
「要几张就调用几次，同题多版就重复调、想要多样性再换 prompt」，两种需求各有自己的动作。

> 首句的量词改了三轮。第十一轮写成「每张**出成的图**都真实扣积分」，是为了避开与
> 「本地就被拒、不扣积分」的字面冲突；第十二轮改成「成功出一张才扣一次积分」，又被
> 指出与「超时、审核拒绝也可能已扣费」互斥；第十三轮干脆**不给首句任何扣费断言**，
> 只写计量方式（「一次调用只出一张图，要几张就调几次」+「`image` 数组的长度只代表
> 参考图张数，永远不能用它凑张数」），扣费整个交给「计费边界」那段的三种说法。
> **同一个事实只能有一种量词；如果一句话在任何一种边界情形下会变成假话，它就不该出现在
> 开场白里。**

**目录为空会直接报错。** `model` 留空时走「该区目录里第一个带对应 tag 的模型」，若该区
目录没有任何带对应 tag 的模型，报的是 `NO_IMAGE_MODEL` 而不是静默降级。描述里说明了
这一点，模型才不会把「留空」当成一定会成功的兜底。

官方 schema 还有 `quality` / `style` / `background` / `footnote` / `revise` 几个字段，
本插件没有暴露：只用目录与实测能确认的东西。

> **仍然没测过的部分**：阈值到底卡在像素数还是某份服务端白名单（`2560x1600` = 4.10 MP 通过、
> `2560x2560` = 6.55 MP 被拒，像是像素阈值，但没有 `2560x1638` 这种临界点样本）；
> 非 8 倍数也没测。工具描述里因此只说「约 419 万像素」这一个实测边界，**不写「支持任意宽高」**。
> 超出范围时上游直接拒绝，错误按 `UPSTREAM` 原样透传。
>
> 下界 `512` 是**产品侧的支持范围，不是实测边界**：512×512 / 512×2048 这类极小尺寸
> 一次都没跑过，写 `MIN_IMAGE_EDGE = 512` 的用途是把「把边写成一个零头」的畸形参数
> 挡在本地（省一次扣积分请求），而不是宣称 512 一定成功。真要放开下界，先补实测。

## 改图（image-to-image）

同一个工具、同一条命令，**给不给 `image` 决定模式**——不新增 `mode` 参数，否则就会
出现「`mode=edit` 但没图」这种自相矛盾的请求：

| 传了 `image`？ | 模式 | 走的端点 | 选模型用的标签 |
| --- | --- | --- | --- |
| 否 | 文生图 | `POST /v2/images/generations` | `text-to-image` |
| 是（非空字符串数组） | 改图 | `POST /v2/images/edits` | `image-to-image` |

`model` 的校验也按当次模式的标签组做：拿文生图模型去改图会直接报
「目录里没有图生图模型「xxx」。可用：…」，不会把不匹配的 id 发上去换一个上游 404。

### `image` 收哪几种形态

官方 CLI 的 `processImageInput` 收下面四种，这里全部支持；**一律先归一成
`data:<mime>;base64,<b64>`** 再发上去（那是上游唯一接受的形态）。
`image` **只收字符串数组**：一张图也要写成 `["/abs/a.png"]`，多张参考图按
数组顺序当参考（如 `[模板图, 服装图]`）——数组会逐张归一后按序传给上游
`/v2/images/edits` 的 `image` 字段（那本来就是 data URL 数组）。

> 为什么不像早先那样「字符串与数组都收」：schema 里的联合类型
> `type: ['string', 'array']` 在只认单 type 的 function-calling 上游会被压平或整段
> 丢掉，模型也会写出 `image: "a.png"` 这种半对半错的值。收敛成单一 `array` 后
> 模型只有一种写法，漏写数组时报错文案直接给出改写结果（`收到的是字符串 "…"，
> 请改写成 ["…"]`）。

数组里混了非字符串或空串、传空数组 `[]`、把 image 写成单个字符串、或传了数字 /
对象等畸形值，一律报 `INVALID_ARGS`，绝不悄悄退回文生图；

| 形态 | 例子 | 说明 |
| --- | --- | --- |
| 本地绝对路径 | `C:\\Users\\me\\pic.png` | 直接读盘 |
| `file://` URL | `file:///C:/Users/me/pic.png` | 先 `fileURLToPath` 再读盘 |
| `http(s)` URL | `https://example.com/pic.jpg` | 宿主侧下载，30 秒超时 |
| data URL | `data:image/png;base64,iVBOR…` | 校验 `data:image/*;base64,` 前缀后原样使用 |
| 裸 base64 | `iVBORw0KGgo…` | 长度 ≥ 100、无路径分隔符、字符集合法才认，否则当成路径 |
| 字符串数组 | `[path1, path2]` | **唯一被接受的形态**；逐张按上表规则归一，按序上传。单图写 `[path1]` |

**上限 8 MB**（`MAX_INPUT_IMAGE_BYTES`），超了报 `INVALID_ARGS` 并在消息里给出实际大小。
体积按**解码后的字节数**算，不按 base64 字符串长度——base64 比原始字节长约 4/3，
拿字符串长度比会把合法的 6 MB 图误判成超限。四条输入路径（`http(s)` / 裸 base64 /
本地路径 / data URL）都过同一个 `assertInputImageBytes()` 闸门，所以「空文件」与
「超限」的文案只有一份、不可能各自漂移。
**不做缩放、裁剪、格式转换**：用户给什么就传什么，免得悄悄改了输入图。mime 的判定顺序
是「HTTP `Content-Type` 的 `image/*`」→「按扩展名」→「按魔数嗅探」（PNG / JPEG /
GIF / WEBP / BMP，兜底 `image/png`）。

### 输入图的失败不进冷却

读不到文件、下载失败、格式不对、体积超限——这些**请求一次都没发出去**，一分钱没花，
所以统一走 `INVALID_ARGS`，不触发 30 秒冷却（冷却只看「请求是否真的发出去了」）。
紧接着再调一次仍然能立刻执行。

> 这条闸门曾经漏掉 data URL 一条路径：`resolveImageInput` 的 `data:` 分支校验完格式就
> `return`，超限的 data URL 会被原样发到上游，再按「已计费失败」吃一次冷却。四条的
> 检查合并到同一个 `assertInputImageBytes()` 之后不再可能各自漂移，回归用例见
> `tests/image-gen.spec.ts` 的「超限的 data URL → INVALID_ARGS」。

### 每组只有一个模型，所以卡片只做只读清单

两个区今天每个标签组都只有 1 个模型（国内区 `hunyuan-image-alpha` /
`hunyuan-image-alpha-edit`，国际区 `hy-image-3.5` 同时带两个标签）。给长度 1 的列表
配下拉框是假选择，所以卡片只显示「这区有哪些媒体模型、各带什么标签」的只读清单
（视频那两个标签组各有 2 个模型，那边是可钉的——见 [VIDEO_GEN.md](./VIDEO_GEN.md) 的「卡片上按模式
钉住模型」）
（`POST /plugins/dsh-connect-workbuddy/media-models`，只读免费，宿主侧缓存 5 分钟，
卡片上的「重新读取」带 `refresh=1` 跳过缓存）。切换能力的方式就是工具的 `model` 参数。

为什么这条端点和 `models/refresh` 分开：聊天目录投影时会把媒体条目丢掉（`selectCliModels`
不认它们），所以刷新聊天目录永远看不到图像模型；这条端点返回的是未经投影的媒体条目。
## 上游协议

请求头（`imageHeaders()`，`src/upstream.ts:1026`）：

```
Authorization: Bearer <accessToken>
Accept: application/json, text/plain, */*
Content-Type: application/json
User-Agent: WorkBuddy/5.8.3 WorkBuddy/5.8.3 CLI/2.161.0
X-Product: SaaS
X-Requested-With: XMLHttpRequest
X-User-Id / X-No-User-Id: 1
X-Enterprise-Id / X-No-Enterprise-Id: 1
X-Domain / X-No-Department-Info: 1
X-Conversation-Id / X-Conversation-Request-Id / X-Conversation-Message-Id: <每请求新 UUID>
```

**刻意不带 `Origin` / `Referer`**：取证探针就是这套头拿到 200 的，多带两个头只是多一个
可能被网关拒掉的变量，没有收益。

请求体按官方 CLI 的 `buildBaseRequestBody` 分支（`buildImageBody()`）：

- `hunyuan-*`：`{model, prompt, size, n: 1}` —— **只**加 `n`，不加 `response_format`；
- `gemini-*`：`{model, prompt, size}` —— 什么都不加；
- 其它：`{model, prompt, size, response_format: 'b64_json'}`。

响应解析（`parseImageResponse()`）：先看信封 `code`（HTTP 200 也可能 `code !== 0`），
再取 `data.data[0]` 的 `url` 或 `b64_json`，最后从 `data.usage.credit` 读实际扣费。
上游给了 base64 时，插件落盘到系统临时目录下的 `workbuddy-image-gen/`
（`os.tmpdir()` 派生，macOS 是 `$TMPDIR`、Linux 是 `/tmp`、Windows 是 `%TEMP%`）
里的 `<model>-<时间戳>.png`，返回 `file://` URL 与本地绝对路径——不让 2 MB 的
base64 直接灌进对话。

## 失败分类与冷却

| HTTP | code | 说法 |
| --- | --- | --- |
| 401 / 403 | `AUTH` | 提示重新登录 |
| 404 | `NO_ROUTE` | 提示该区没有生图路由 |
| 429 | `RATE_LIMIT` | 提示限流 |
| 其它 | `UPSTREAM` | 抽信封里的 `msg` |

冷却只对**真的发过请求**的失败生效（`AUTH` / `RATE_LIMIT` / `NO_ROUTE` / `UPSTREAM` /
`EMPTY_RESULT`，以及非本模块的异常）。参数写错、未登录、目录里没有模型这三类**不进冷却**
——它们一分钱没花，冷却只会让人以为工具坏了。

## 安全

- **凭据不出宿主进程**：工具在宿主侧执行，token 只用于这一次 `fetch`，不进对话上下文、
  不进页面。与积分读数那条链路的边界一致。
- **桌面 App 的认证文件始终只读**：`WORKBUDDY_AUTH_FILE` 只在测试里用来指向它，
  生产路径读的是插件自己的凭据库。

## 没做的事（如实登记）

- **视频（`/v2/videos/generations`）现已独立成工具 `workbuddy_draw_video`**，
  详见 [VIDEO_GEN.md](./VIDEO_GEN.md)。它的要点是：**视频是异步任务**，不是同步生图——
  `submitVideo()` 只拿到 `taskId`，还要 `pollVideoTask()` 轮询到 `completed`、
  再 `downloadVideo()` 把视频拉到本地才算完成。旧版本文档里写的「加视频只是接一次
  `submitVideo()`」少了轮询 + 下载两段，已在 VIDEO_GEN.md 的「与『只接一次 submitVideo()』
  的旧说法对账」一节纠正。参数层与选模型层（`MEDIA_TAGS`、`VIDEO_TAG_*`、卡片清单、`fetchMediaModels`）
  确实可复用，但执行层是全新异步代码；卡片的视频行也与图像行不同，可按模式钉模型。
- **国际区已支持**（2026-10-25 起）：国际区目录里的 `hy-image-3.5` 带 `text-to-image`，实测可用；
  此前「国际区一条都没有」的观测已过期，不要再据此禁用它。
- **不做批量**：一次调用一张图、一份积分。没有「一次画四张」的参数——那是一次不可控支出。
