感谢反馈，截图里的对照很说明问题——trae 有、workbuddy 没有，而这两个插件在同一个作者手里。
先说结论：**数据一直都在，只是没渲染出来**，现在已经补上了，两处。

## 一、你说得对：这是"没显示"，不是"没算"

workbuddy 的积分汇总（`WorkBuddyCredits`）一直带着两个字段：

- `expiringSoon`：3 天内会过期的积分合计；
- `nearestExpiryMs`：所有积分包里最近的一次到期时刻。

账号池的成员行也早就在打印 `{count} 积分 3 天内过期`。所以缺的从来不是计算，而是两个表面：

1. **编写器（composer）的账号面板**——那张表每行只印余额，没有任何临期信息；
2. **卡片的「账号」分区**——完全没有临期提醒。`status.credits` 一直在文档里，但卡片只读过
   `status.creditsError`，余额字段一次都没被渲染过。

这两处现在都补上了。另外，账号积分路由（`workBuddyAccountCredits`）原本只回传 `total`，
现在每个账号额外带回 `expiringSoon` 与 `nearestExpiryMs`——它是编写器面板唯一的来源，而且对
**不在池里的账号**（池子的 `otherAccounts` 不带余额）这是唯一的来源。

## 二、效果

- **编写器面板**：余额下面多一行小字，`300 积分 3 天内过期`。
- **卡片「账号」分区顶部**：一条琥珀色横幅，点名账号 + 数量 + 最早到期时刻。

措辞直接**复用账号池的 `row.poolCreditSoon`**，没有另写一套。同一个事实、同一次测量，两处
如果各写一套话术，读者就得先分辨它们讲的是不是一件事。

## 三、一处刻意的取舍：行内只说数量，日期只在悬停里

这一点和你贴的 trae 横幅不完全一样，说明一下原因。

5.20.22 有过一次明确决定：账号行里那行「最近积分包 11/27 03:46 过期」被**按用户要求撤掉**了——
它在每个账号上都占第二行，而那个日期几个月后才到，没人在拿它做决定。留下的是**能据以行动的
数量**。

所以这次严格沿用：面板每行仍然只印数量，绝对时刻进整行的 `title`（悬停可读、屏幕阅读器可读），
**不**打印出来。卡片横幅是唯一例外——那里只出现一次（为一个账号），而不是每行一次，所以允许
同时印出数量与最早到期时刻，也就回到了你截图里那种两行结构。

## 四、一个容易踩的坑：触发条件只能是 `expiringSoon > 0`

`nearestExpiryMs` 是**所有**积分包里最近的一次到期，所以一个**没有任何积分要过期**的账号照样
可能带着一个未来日期（月度包到期后会刷新，从不真正过期）。因此两处展示都只认
`expiringSoon > 0`：

- 余额没读到时（`credits` 缺失）**什么都不显示**——「0 积分过期」是一次测量结论，不能替一个
  没人测量过的账号下这个结论，那会让本该显示「—」的行宣称用户积分安全；
- 只有日期、没有数量时**什么都不显示**——否则就是 5.20.22 撤掉的那行日期卷土重来。

这两条都有守护测试，并且做了变异验证（改坏映射、改坏触发条件、去掉账号名，测试都会变红）。

## 五、关于 trae 那套四档梯度

trae 的实现是四档（24 小时 / 3 天 / 7 天 / 已过期）+ 区域级横幅。这里**没有**照搬那套梯度，
原因是你的原话是「简单表达出来」——四档梯度在行内会变成四套措辞，而真正需要用户动手的只有
「有积分马上要没了」这一件事。如果你实际用下来觉得 7 天那一档也有用，可以再开一条 issue，
那是独立的改动。
