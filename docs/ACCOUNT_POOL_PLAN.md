# 账号池（Account Pool）功能规划 —— 国内版

> ⚠️ **本文是 3.0.0 时的原始规划，保留作设计过程的记录，不再是当前行为的依据。**
>
> 其中第四节「自动轮换策略」（含 4.1、4.2 的「与手动选择互斥」、4.5 的「自动测试的时间间隔」）**已被取代并删除**：产品改为**开启账号池即开启自动换号** —— 请求在上游失败时依次用池内其他可用账号重试，直到有人接手或全部不可用。与轮换的关键区别是「按请求借用」而非「持久改选」，因此：
>
> - 不再有 `rotateByCredits` 与 `autoTestIntervalMinutes` 两个设置项，也不再有任何定时器；
> - 不再与手动选择互斥（手动选择始终有效，卡片上的「当前账号」就是用户选的那个）；
> - 4.1 里那条「绝不静默换号」的原则**仍然有效**——换号不写回选择，只是为一次请求借用别的账号的额度。
>
> 当前行为以 [README](../README.md#账号池)、`CHANGELOG.md` 的对应条目与 `src/shim.ts`（重试循环）+ `src/index.ts`（`failoverAccountFor`，候选策略）为准。第四节以下的其余内容（两个批量动作、池成员显式勾选、区域独立、目标模型解析、保存语义）**大体仍然成立**。

> 目标：在 `dsh-connect-workbuddy` 插件**国内版 tab** 中新增「账号池」能力，提供两个动作 + 一套自动轮换策略。
> 本文只做规划，不改动现有运行时行为。演示界面见 [`docs/assets/account-pool-demo.html`](assets/account-pool-demo.html)。

## 1. 现状盘点（已具备的地基）

本机插件本身已经跑通了账号池需要的大多数底座，新功能是**编排**而不是重造：

| 能力 | 现有实现 | 对本功能的意义 |
| --- | --- | --- |
| 枚举本机多账号 | `WorkBuddyAccountStore.accounts()` → `WorkBuddyAccountChoice[]` | 账号池的「池成员」来源，token-free，可直接下发到浏览器 |
| 按 id 取凭据且**不切换选中** | `credentialFor(accountId)` | 签到/测试可以针对**任意账号**执行，而不必先选中它（关键：否则测一个换一个） |
| 每日签到 | `POST /v2/billing/meter/daily-checkin` + `fetchCheckinStatus()` | 「一键签到所有账号」逐个调用即可 |
| 签到状态 | `checkin-activity-status` | 幂等判断，避免重复领取 |
| 积分 | `fetchCredits()` → `WorkBuddyWebCredits{total, packages, expiringSoon, nearestExpiryMs}` | 「按积分轮换」的排序键 |
| 模型可用性测试 | `probeModel()` / `WORKBUDDY_PROBE_PATH` | 「测试 deepseek-v4.1-flash 是否可用」直接复用，含 `rate-limited` / `out-of-credit` 的**上游真实恢复时间** |
| 区域路径 | `withWorkBuddyRegion()` / `regionOfStatusUrl()` | 所有新路由沿用 `?region=` 约定，国际版可零成本复用 |

`deepseek-v4.1-flash` 已在国内版 catalog 中（`src/catalog.ts:59`，`creditMultiplier: 0`，即**免费**），所以「一键测试所有账号」的默认目标模型就是它。

## 2. 功能一：一键签到所有账号

**行为**：对池中每个账号，串行执行一次签到。

流程（单账号）：

1. `credentialFor(accountId)` 取凭据；token 过期则先走既有 refresh 路径。
2. `fetchCheckinStatus()` —— 若 `todayCheckedIn === true`，直接标记 `already`，**不发写入请求**（幂等，不浪费）。
3. 未签到则 `daily-checkin` 领取，记录 `todayCredit` / `streakDays`。
4. 任何异常（401 / 网络 / 上游 5xx）只标记该行失败，**不中断整批**——这是 `probeModel` 已经确立的原则：一个坏账号不能掩盖其余账号的结果。

**串行而非并发**：签到是写操作，且上游有频率限制；并发签到正是把整批打成 429 的最快方式。逐账号串行 + 每个账号之间留一个小的固定间隔。

**幂等与安全**：签到是**写入**，因此
- 路由必须是 `POST`，且沿用既有 `loopbackOrigin(req)` 回环来源校验；
- **不提供定时自动签到**（完全不做，不是「默认关闭的开关」）——见第 5 节。

## 3. 功能二：一键测试所有账号 × 该区域的免费模型

**行为**：对池中每个账号，用**该区域自动挑出的倍率为 0 的模型**（见 4.4；默认不是写死的模型 id）发一次真实体积的探测请求，得出该账号该模型此刻**是否可用**。

直接复用 `probeModel()`，因此天然继承三个实测结论：

- 首条消息必须是 `system`（否则国际网关整片误报不可用）；
- 限流恢复时间从**响应体**里解析（`将在 … 重置`），而不是响应头；
- 探测发的是**真实体积**（25k input），避免「探测通过、真实长会话被限流」的假阳性。

**结果四态**（就是现有 `WorkBuddyProbeOutcome` 的语义）：

| 状态 | 含义 | 对轮换的意义 |
| --- | --- | --- |
| `ok` | 此刻可用 | **可入选**，记录 `elapsedMs` |
| `rate-limited` | 模型没问题，只是被限流 | **暂时出池**，按上游给出的重置时间回池 |
| `out-of-credit` | 积分耗尽 | **出池**，按 `quota-refresh` 时间回池 |
| `credential-rejected` / `unavailable` / `failed` / `not-found` | 凭据或链路问题 | 出池，并提示重新检测账号 |

> 关键点：`rate-limited` ≠ 不可用。若把它当成「不可用」就永久剔除，正好丢掉功能想利用的那些账号。

每次探测有真实成本（实测 `credit: 0.72`，而 v4.1-flash 的倍率为 0，实际近乎免费）。即使如此，界面仍如实标注「每次测试会产生真实请求」。

## 4. 自动轮换策略

**排序键优先级**（这是本功能的核心规则）：

1. 该账号对 `deepseek-v4.1-flash` 的**最近一次探测是否 `ok`**（不可用者直接出池）；
2. **积分余额**高者优先——积分少的账号先留着，别把余额耗在它身上；
3. **可用时间窗**（`nearestExpiryMs` / `expiringSoon`）——快过期的积分优先用完，否则等于白扔；
4. 平手时按 `tokenExpiresAtMs`，凭据更新鲜者优先。

三者合成一个得分，得分最高者作为**当前计费账号**。这需要在既有的「不静默切换账号」的约束下小心实现——见下。

### 4.1 与既有「绝不静默换号」原则的冲突与解法

现有代码里有一处非常明确的设计（`src/auth.ts:875`）：

> **This is NOT credit-seeking** — it never reorders accounts to find one with remaining credit.

也就是说，插件**当前刻意不做**按积分选账号，因为它会让「账单落在哪个账号上」变得不可预测。

账号池功能正是一次**用户显式要求的**例外，因此必须：

- **默认关闭（opt-in）**。自动轮换是一个显式开关，用户打开即视为授权「可以按积分为我换号」。
- **轮换必须可见**。每次切换都要在界面上留下一条记录（何时、从谁到谁、为什么），而不是悄悄发生。
- 关闭开关后，行为**完全回到现状**：跟随 WorkBuddy 桌面端当前登录，不按积分重排。

### 4.2 与「手动选账号」的冲突（关键设计）

手动选账号在插件里不是临时状态，而是**持久化的区域配置**：`config.accounts[region]`（`src/index.ts` 的 `accounts` 槽），由卡片下拉写入、由 `WorkBuddyAccountStore.current()` 读取。也就是说 —— **手动选择和自动轮换会争夺同一个位子**（"这个区域用哪个账号计费"）。

若两者同时生效，用户会看到最坏的一种状态：**下拉里显示账号A，但实际计费的是账号B**。这正是既有代码极力避免的"看起来正常、其实不是所选项"（见 `src/client/WorkBuddyCard.tsx` 里关于 orphaned id 的注释：a picker that lies）。

**因此规则是：同一区域内，自动轮换与手动选择互斥，自动轮换开启时手动选择必须被禁用并说明原因。**

具体交互：

1. **自动轮换开启 → 下拉置灰**，并在其下方显示提示：
   > 已开启自动轮换，账号由插件按积分自动选择。要手动指定账号，请先关闭「按积分自动轮换」。
2. 提示旁给一个**就地关闭**按钮，不让用户去别处找开关（减少摩擦，也保证他确实看到了冲突原因）。
3. **关闭自动轮换后**，手动下拉立即恢复可用，并**回到用户上次的手动选择**（`config.accounts[region]` 里的值不被轮换过程改写）—— 这点很重要：轮换只在运行时决定"用谁"，**不写入 `accounts` 槽**，因此不会污染用户的选择记录。
4. 若用户在自动轮换开启期间**试图操作**已禁用的下拉，提示文案即上面的冲突说明，而不是静默无反应。

**实现上的关键约束**：自动轮换**绝不写 `config.accounts[region]`**。它只影响运行时 `current()` 返回哪个凭据。这样"关闭自动轮换"就是干净的：用户上次的手动选择原封不动地回来。若轮换去改写那个槽，用户的显式选择就被永久覆盖了，且无法区分"用户选的"和"插件换的"。

这与既有的「绝不静默换号」原则是同一个精神：**运行时可以按规则换号（用户已授权），但用户的显式选择记录不被篡改。**

### 4.2.1 保存语义：不是所有状态都该等"保存"

需求里说"自动轮换的选择变化之后要保存"，要落成代码必须先把池里的状态**分成两类**——因为插件现有的两种写入模式（`src/client/`）语义完全不同，混用会出事：

| 类别 | 池里的字段 | 写入方式 | 理由 |
| --- | --- | --- | --- |
| **草稿**（用户可改、点保存才生效） | `enabled`（池开关）、`rotateByCredits`（自动轮换开关）、`autoTestIntervalMinutes`、`targetModelId` | **草稿 + 显式保存** | 与「模型管理」一致：用户可以先调整再决定 |
| **运行时事实**（不是用户偏好，是观测结果） | 每个账号的最近探测结果、`credits`、`cooldownUntil`、`lastTestedAt`、当前轮换到的账号 | **自动落盘，不经过保存按钮** | 它由插件自己写入，没有"草稿"一说 |

**为什么必须分开**：模型管理用的是「草稿 → 保存 → 丢弃草稿」模式，而保存成功会**丢弃草稿**（`saveModels()` 里 `discardModels()`）。如果运行时事实也走草稿，会出现荒谬的结果——用户手工点一次"保存"，可能把定时器刚写进去的探测结果**回退成几分钟前的旧值**，因为草稿是唯一的副本、覆盖式的。

所以：

- 探测结果与轮换事实由 **Host 侧**在每次测试后写入自己的存储（不进 `regions[region]` 的用户草稿区），卡片只读显示；
- 用户的四个偏好字段走既有的 `writeRegionModels` 同款"**验证写入 + 失败保留草稿**"路径——写入不成功时**不能丢弃草稿**，否则用户的编辑就永久丢了（`writeAccountSlot` / `writeRegionModels` 的注释里对这个静默失败有专门处理，池必须沿用同一套）。

**"变化之后要保存"的准确含义**（这是需求里的关键点）：

1. **用户改动四项偏好 → 必须点保存才落盘**，并显示 dirty 指示；未保存就切 tab/关卡片，草稿保留（与模型管理一致）。
2. **自动轮换发生的换号 → 立即落盘**，但它写的是**运行时事实**，不是 `accounts` 槽。因此"保存"与"换号"不会互相覆盖：换号不动用户的 `accounts` 记录，保存也不回退刚发生的换号。
3. **定时测试写回的探测结果 → 立即落盘**，同样不进草稿区。

这样"自动轮换的选择变化之后要保存"就成立了，而且**不会**和「保存会丢弃草稿」这个既有语义打架。

### 4.2.2 两个「保存」按钮：各自保存自己的内容，但互相串行

卡片上有**两个**保存按钮（模型管理一个、账号池一个），这是刻意保留的，而不是合并成一个：

1. **草稿域不同**。模型草稿和池草稿是两个独立域，合并成一个「保存」会让一次失败牵连另一边
   —— 模型目录写入失败会连累你保存不了池偏好。
2. **放弃的爆炸半径**。一个共享的「放弃」会在一次误点里同时丢掉两份草稿。
3. **卡片本来就有混合写入语义**：账号选择器和区域开关是即时写入，模型是草稿+保存。
   各自区块管各自的保存是这张卡片的既有模式。

但两个按钮**共写一个区域槽**（`regions[region]`），且 Host 的 `__save` 是**按区域合并**
（保住兄弟区域，但同一区域的槽内容整体来自调用方）。因此两条硬性规则：

- **每个写入方都先把新内容合并到现有槽上**（合并基准在写入函数内部从 settings 快照读取，
  调用方不可能忘记传）—— 这是关键修复：旧的模型保存曾**整槽替换**，会无声地删掉
  同槽里的池设置。模型列表、供应商开关、池偏好三者互相保留，有共存测试钉住。
- **两个保存按钮互相串行**：一个在写，另一个禁用（`siblingBusy` / `onBusyChange`），
  把"同时点击互相覆盖"从"可能"变成"不可能"。
- 池保存成功后立即 `refreshUsage`：池状态来自 usage 路由，不刷新的话 UI 会回退到旧值
  直到下一轮 60 秒轮询，看起来就像"保存没生效"。

### 4.3 国内版 / 国际版各自独立

两个区域各自拥有一整套账号池（这正是插件既有的双区域结构：`cn` / `global` 各自的凭据 store、catalog、adapter）。因此：

- 账号池开关、自动轮换开关、测试间隔、目标模型 **全部按区域独立**；
- 国内版 tab 的池只含国内版账号，国际版 tab 的池只含国际版账号（凭据按域名归属隔离，见 README 的区域划分规则）；
- **一个区域的自动轮换不影响另一个区域**——国内版可以开着自动轮换，同时国际版保持手动；
- 定时器也是**每区域一个**，各自按自己的间隔跑。

配置落在各区域的槽里，与 `regions.cn` / `regions.global` 的既有结构一致：

```
regions: {
  cn:     { enabled, lastCatalog, enabledModelIds, ..., pool: { ... } }
  global: { enabled, lastCatalog, enabledModelIds, ..., pool: { ... } }
}
```

### 4.4 目标测试模型：按区域 catalog 自动挑免费的

**默认不写死 `deepseek-v4.1-flash`，而是从该区域当前的 catalog 里自动挑一个倍率为 0 的模型。**

理由是两个区域的免费模型**根本不是同一个集合**（`src/catalog.ts`）：

| 区域 | 倍率为 0 的模型（静态 fallback 实测） |
| --- | --- |
| 国际版 | `deepseek-v4.1-flash`、`hy4-preview`、`hy3` —— 三个 |
| 国内版 | 静态 fallback **一个都没有**（该列表只带 `id/name/contextWindow/maxTokens`，不含 `creditMultiplier`） |

国内版静态列表不带倍率是有原因的：倍率来自上游 `credits` 字符串（如 `x0.00`），由 `parseCreditMultiplier()` 在**刷新时**解析（`src/upstream.ts:510`）。所以国内版的免费模型**只有 live refresh 之后才知道**。

**挑选规则**（按优先级）：

1. 在 `regionStateOf(config, region).lastCatalog` 里筛 `creditMultiplier === 0`；
2. 多个候选时取**上下文窗口最大**的一个（`contextWindow`），大窗口更能承载真实长会话，且探测本身发 25k input；
3. 平手则按 catalog 顺序取第一个（稳定、可预测，不引入额外随机性）。

**两个必须处理的边界**：

- **没有任何倍率为 0 的模型时**（国内版在首次刷新前就是这种状态）：**不静默回退到收费模型**——那会让「一键测试所有账号」变成一笔用户没预期的开销。此时卡片显示"本区域暂无免费模型，请先刷新模型目录"，并允许用户**手动指定**一个目标模型（此时明示其倍率）。
- **用户手动指定过目标模型时**，自动挑选不再覆盖它。自动挑选只负责"默认值"，与手动选择的关系是：手动 > 自动。这跟 4.2 的账号互斥规则不同——目标模型是纯偏好，不存在"两个位子打架"的问题。

`creditMultiplier` 为 `undefined`（上游没给倍率）**不等于免费**，必须严格判 `=== 0`，不能把缺失当 0。

### 4.5 自动测试的时间间隔

- 间隔可配置，默认 **30 分钟**，下限设一个保护值（如 5 分钟），避免把账号测成 429。
- 定时器只在**开关打开**时存在；关闭即 `clearInterval`，不留后台任务。
- 定时测试**只测当前池成员**，且串行。
- 若某账号返回 `rate-limited` 并给出了上游重置时间，则在那之前**跳过它**，而不是到点再撞一次墙。

### 4.6 池成员是显式勾选，默认一个都不含

账号池**不等于"本机全部账号"**。成员是一份显式的勾选清单（`memberAccountIds`），
**默认为空**，卡片上每个账号一个复选框并带「全选 / 全不选」。

理由是这两个动作都有真实代价：签到会代表用户领取奖励、测试会消耗积分。让"我在这台机器登录过"
变成"于是这些账号都会被操作"，是把用户没授权的开销当成默认值。因此：

- 未勾选的账号**不被签到、不被测试、也不参与轮换**（轮换只在池成员里挑人）；
- 池为空时两个按钮**在 UI 和 Host 两侧都禁用/拒绝**——"一个都没勾"绝不能退化成"那就全都做"；
- 未勾选的账号**仍然列在卡片上**（标为"未入池"），否则用户没有入口去勾选，opt-in 就不成立。

配置：`regions[region].pool.memberAccountIds: string[]`，默认 `[]`。

## 5. 不做的事（明确边界）

- **不提供自动签到**：签到是写操作，会真实领取奖励，因此只由用户手动点按钮触发。
  卡片上**不展示**这个开关——一个永远点不动的控件会让人误以为「有这功能但被锁住」；
- 不在关闭开关时按积分重排账号；
- 不编造恢复时间：上游没说就显示「上游未给出」，与 `cooldownOf()` 的既有契约一致；
- 不把 `rate-limited` 当作永久不可用；
- **不把「本机有登录」当成「加入账号池」**：成员必须显式勾选，默认空；
- **空池不执行为「全部」**：没有勾选时两个批量动作都必须拒绝，而不是回退到全账号；
- **轮换不写入 `config.accounts[region]`**，绝不篡改用户的手动选择记录；
- **自动轮换开启时不接受手动选择**，两者不并存（见 4.2）。
