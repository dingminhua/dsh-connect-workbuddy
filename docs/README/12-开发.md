## 开发

```sh
pnpm install
pnpm run check   # typecheck + test + build
```

本地开发用 `link:` 安装到 desktop profile（改码后重启 DSH Desktop 生效）：

```sh
dsh plugin --profile desktop add /Users/<you>/DshProject/dsh-connect-workbuddy
```

#### `link:` 安装必须先构建，否则 DSH 会拒绝加载

`lib/` 是构建产物且被 gitignore，而 `link:` 安装**不执行包的生命周期脚本**（`prepare` 不会跑）。
于是从一份没构建过的源码检出安装时，`package.json` 里声明的 `main` / `exports` 指向的文件并不存在，
DSH 的插件市场据此判定：

```
声明的入口产物缺失(源码检出或构建被拦),下次启动会失败
```

这个判定来自 `dshmarket` 的 `entryArtifactExists()`——它只读安装目录里的 `main` 与 `exports`，
文件在不在就是全部依据。所以：

```sh
pnpm install        # prepare 会构建一次（lib/ 出现）
# 或只构建
pnpm run build
```

改完源码也要再 `pnpm run build` 一次（或重跑 `pnpm install`），然后重启 DSH Desktop。
`pnpm install` 之后仍报同样的话，先跑这一条自查——它打印每个被声明的产物在不在，
并区分「从没构建过」和「manifest 与构建不一致」两种原因：

```sh
pnpm run verify:entries                                   # 当前仓库
node scripts/verify-entry-artifacts.mjs <已安装的目录>      # 具体某个安装副本
```

> 从 npm 安装（`dsh plugin add dsh-connect-workbuddy`）不需要这一步：发布包里 `lib/` 已经在，
> `prepack` 也只负责把它重新生成一遍。

### 宿主心跳：清理由**写入它的那个实例**负责

`writeHostHeartbeat()` 在 `$DSH_HOME/.workbuddy-host-heartbeat.json` 写一份宿主回执，`doctor` 据此判断宿主是否活着。它的 `dispose` **不再无条件删除这个文件**，而是只删自己那次成功写入的那一份。

原因是三类真实故障都出自「谁都能删」：

- **启动失败也要清理**：注册抛错时没有回执可清，删掉的是**另一个仍在运行的宿主**写的文件；
- **两个宿主先后写同一文件**：后写的那个先退出，旧实例一删，新宿主的回执就没了，`doctor` 报「宿主未运行」；
- **写入是异步的**：`dispose` 在写入落盘之前就完成时，清理反而删不到东西，过一会儿旧记录又出现。

所以：

```ts
const owner = await writeHostHeartbeat()   // 返回 { path, contents }
// …插件存活期间…
await clearHostHeartbeat(owner)            // 只删这份；文件已变、已消失或 owner 为空时什么都不做
```

- 文件路径在**写入时**捕获，所以之后改 `DSH_HOME` 不会把清理重定向到别的目录；
- 字节比对不通过（别的实例已覆盖）就**保留当前文件**，这就是「新宿主不会被旧实例删掉」的全部实现；
- 读取失败里只有 `ENOENT` 被视为正常，其他错误照常抛给调用方；
- 每次写入带一个 `registrationId`（UUID），用来区分同 PID、同一毫秒内的两次注册。它是**只写不读**的字段：`readHostHeartbeat()` 的 v2 字段与版本判定都没变；
- 真实 disposer 会先 `await` 未完成的写入再清理，写入失败只记一条 error 日志，实例随后不带 owner 退出。

**已知边界：跨进程原子互斥没有做。** 「读 → 比对 → 删」之间仍有一个很窄的窗口，外部进程可以在这个窗口里替换文件。本改动保证的是**实例归属**，不是互斥；要彻底消除这个窗口得另设计一套跨进程锁，不在这一版的范围里。

### 写脚本调用 `chatStream()` 时注意：它返回的是**信封**，不是可迭代流

```ts
const envelope = await client.chatStream(credential, bodyJson)
if (!envelope.ok) { /* 失败：envelope.status / .kind / .message / .detail */ }
else { await envelope.response.text() /* 或者按 SSE 消费 */ }
```

**先查 `envelope.ok` 再消费** —— 它返回 `{ ok: true, response }` 或 `{ ok: false, status, kind, message, detail }`，而不是一个可以直接 `for await` 的流。跳过这一步的典型后果是**把失败全报成成功**（`response` 是 `undefined`，读它会抛错或被吞掉，于是「每个模型都成功」）。这条来自 issue #56 报告者的实测提醒，写在这里是为了让下一个人少踩一次同样的坑。

失败信封里的 `kind` 就是本文提到的失败分类（`soft_rate` / `model_busy` / `hard_credit` / `session_dead` / `policy_reject` / `not_found` / `server` / `client`），`detail` 携带上游的 `upstreamCode` / `requestId` / `displayMsg`。
