## 安装

> ⚠️ **版本要求：DSH 0.1.7-rc.1 及以上（当前窗口：`0.1.7-rc.1` ~ `0.2.x` 正式版）。** 自 v2.1.0 起本插件只支持 DSH 0.1.7-rc.1 及以上的宿主（旧版宿主无法通过依赖解析安装本版）；0.1.5 及更早的宿主请停留在 v2.0.15。自 v2.1.2 起上界放宽为 **`<0.3.0-0`**，0.3.0 线被明确拒绝。详见下方[受支持的宿主范围](#受支持的宿主范围)。

> ⚠️ **国内区的「渠道校验」400（`code 11128`）请确保插件 ≥ 5.14.0。** 5.13.1 起会在**发出请求之前**按句改写已知的固定指纹，5.14.0 又补上了 Web GUI 段落的第二句（#167，5.13.1 上仍然必现的那一支）；5.12.x 及更早只有「中性头 + 零宽扰动」三级救援，在同一份 body 上实测**全部 400**（对照矩阵见 [#164](https://github.com/dingminhua/dsh-connect-workbuddy/issues/164)）。停在旧版的人会反复撞上这个已经修好的 400，而表现是「每次必现、重启也没用」。
>
> **升级后若仍被拒：从源头关掉宿主注入的身份句。** 网关按提示词**中段任意位置的精确子串**匹配，而固定在每个会话里的 first-party 身份句（`You are an AI agent powered by DeepSeek Harness.`、Web GUI 段落、模型 persona 行）会被逐轮原样重发，插件的改词表只能覆盖已知指纹。宿主 `dsh-system-prompt` 服务支持在 profile 里关掉这三类注入（#293 的报告者验证：三项全关、重启宿主、开新会话后 11128 消失）：
>
> ```yaml
> - id: system-prompt
>   name: "@deepseek-ai/dsh-system-prompt"
>   config:
>     includeHarnessIdentity: false
>     includeRuntimeContext: false
>     personaPrefix: "You are a helpful assistant."
> ```
>
> 这三项属于宿主服务的配置、不是本插件的行为，写在你自己的 profile 里；关掉后这些句子不再进入 system 消息。改不了配置时，**开一个全新会话**是有效临时规避——被污染的 assistant 历史是这类中段命中的常见载体，而它会被写进会话文件、重启也不消失。
>
> 若前三项关掉仍被拒，还有第三个面：**回放的 thinking**。网关扫整份请求文本，而多轮会话会把上一轮的 `reasoning_content` 原样重发；本插件设置项 `dropAllThinking` 打开后不再回放这部分（代价是模型看不到自己之前的思考过程，需要连续推理的任务会受影响）。报错里的「零正文指纹线索」现在也会标出 `reasoning_content` 里的命中（带字段后缀），可据此判断是否需要开它。
>
> ⚠️ **别把插件市场里那个「最新」当日程表——它读的是一份会落后的索引。** 社区市场走定期构建的快照（按包各自收录），2026-10-30 15:00 那次观测里本插件还停在 5.13.1，而当时 npm `latest` 已是 5.14.1；桌面宿主另有「24 小时内发布的版本先标成「新版等待中」」这条规则。以 `npm view dsh-connect-workbuddy version` 与 [Releases](https://github.com/dingminhua/dsh-connect-workbuddy/releases) 为准，按下方[「更新」](08-更新.md#更新)一节做（写**精确版本号**），或者把 [`docs/PINNED-UPGRADE-LAG.md`](../../docs/PINNED-UPGRADE-LAG.md) §3 那段话丢给 AI 让它替你跑。
>
> 另一个会让人升级不到的原因：**pnpm 的 24 小时新版本等待期**（`minimumReleaseAge`）会把浮动范围**静默压回上一个版本**。需要立刻修复时请写**精确版本号**：`dsh plugin --profile desktop add dsh-connect-workbuddy@5.20.2`（原因见下方「刚发布的版本请写精确版本号」那条）。

### 受支持的宿主范围

DSH 的随包门禁（`packages/boot/app-boot/src/plugin-compatibility.ts` 的 `evaluatePluginCompatibility`）会逐条核对本插件声明的 `dsh-*` peer 范围；**只要有一条不满足，整个组合包会被跳过**（进入 `skippedBundles`，仅打印到 stderr）——provider 不注册、卡片不出现、模型列表清空，而页面上没有任何报错。

| 宿主版本 | 判定 |
| --- | --- |
| `0.1.7-rc.1` ~ `0.1.7-rc.2` | ✅ 支持 |
| `0.2.x` **正式版**（`0.2.0`、`0.2.1` …） | ✅ 支持（2.1.2 起实测） |
| `0.2.x` **预发布**（`0.2.0-rc.1`、`0.2.1-rc.1` …） | ⚠️ 不落在声明范围内，见下方说明 |
| `0.3.0-0` 及以上 | ❌ 明确拒绝（该线尚未验证） |
| `0.1.6` 及更早 | ❌ 明确拒绝（0.1.5 线请停留在 v2.0.15） |

> **`0.2.2-rc.1` / `0.2.2-rc.2` / `0.2.2-rc.3` 已实测可用**（5.24.0）；**`0.2.2-rc.4` /
> `0.2.2-rc.5` 已复核可跟进**（5.25.0，详见
> [`docs/DSH-0.2.2-RC5-FOLLOWUP.md`](../../docs/DSH-0.2.2-RC5-FOLLOWUP.md)）：各版的随包门禁都把现声明判为
> ADMITTED，插件在运行中的宿主上完整加载（16 条路由、8 个槽位里的 6 处、客户端模块全部注册），
> 本仓库套件也在 `0.2.2-rc.5` + pi-ai `1.3.0` 的真实组合上全绿。上表那行「⚠️ 不落在声明范围内」
> 描述的仍是**裸 semver** 的判定，与「能不能跑」是两件事，原因见下条。

> **关于 `0.2.x` 预发布（v4.7.0 更正）**：此前本表把 `0.2.0-rc.1` 写作「✅ 支持」，那是**错的**。
> npm semver 规定：预发布版本只有当一个比较器**在同一条 `major.minor.patch` 元组上**带预发布标签时才被放行。
> 现声明 `>=0.1.7-rc.1 <0.3.0-0` 只对 `0.1.7-x` 开口，`<0.3.0-0` 又排除了 `0.3.0` 元组，因此
> **`0.2.1-rc.1` 这类版本两条比较器都不满足**（`satisfies('0.2.1-rc.1', …) === false`）。
> 实际影响很小：宿主门禁只校验 `@deepseek-ai/dsh*` 命名空间（其余 peer 不参与），而它对这批 peer
> 的范围求值用的是 `semver.satisfies(rt, range, { includePrerelease: true })`，所以 rc 宿主照旧
> **放行**——闸门确实校验了，只是用 `includePrerelease` 放过（归因订正见
> [`docs/DSH-0.2.1-RC3-FOLLOWUP.md`](../../docs/DSH-0.2.1-RC3-FOLLOWUP.md) §3）。
> 这**不是**靠改范围能解决的问题——任何静态范围都覆盖不了「任意 `0.2.x` 预发布」，已逐一实算否证五种写法
> （见 CHANGELOG 4.7.0）。等宿主发 `0.2.1` 正式版即自然成立。

> 上界写作 `<0.3.0-0` 而非 `<0.3.0`：DSH 至今**全部 tag 都是预发布**（`-alpha.N` / `-rc.N`），只写 `<0.3.0` 会放行整条 `0.3.0-alpha.1` / `0.3.0-rc.1` 这条从未验证过的线，围栏形同虚设——这正是 2.1.2 修掉的缺陷形状。该口径由 `tests/dsh-line.spec.ts` 守卫（含预发布悬崖的用例）。

> 🪟 **平台支持：Windows、macOS、Linux 三者并列支持。** **Windows 是一等目标平台**，不是「顺带能跑」：CI 在 `windows-latest` 上跑完整套件，凭据路径、进程心跳、App 可执行文件定位、设置写入四处都有 Windows 专属分支与测试，并且**修复只对 Windows 生效的缺陷时，以 Windows 用户回报的现场与真机取证的加密向量为准**（见 [CHANGELOG](../../CHANGELOG.md) 的 2.0.6 / 2.0.11 / 2.0.12 各节）。见下方[平台支持](09-平台支持.md#平台支持)一节了解各平台的具体差异与已知限制。

前置：已安装并登录 WorkBuddy 桌面 App（插件复用 App 的登录状态）。

推荐使用 DSH 插件命令安装 npm 已发布版本：

```sh
dsh plugin --profile desktop add dsh-connect-workbuddy
```

或直接通过 npm 安装：

```sh
npm install dsh-connect-workbuddy
```

安装、更新或卸载 bundle 后，需要重启对应的 DSH 进程。

安装完成后的配置入口在**设置面板左侧导航的「WorkBuddy」**（与「账号与余额 / 通用设置 /
模型 / 插件」等页面并列）。插件市场里那个 bundle 详情页从 5.19.0 起**不再显示配置卡片**——
同一份配置只留一个编辑入口。侧边栏底部那个「设置」入口打开的就是这个面板。

> ⚠️ **刚发布的版本请写「精确版本号」，不要依赖浮动范围。** pnpm 有**新版本等待期**（`minimumReleaseAge`，默认 24 小时），所以一个版本刚发布不久时，浮动范围会被**静默压回上一个版本**：声明 `^4.4.2` 时它仍解析到 `4.4.2`，而写精确的 `4.4.3` 则立即拿到 `4.4.3`。由于**两种写法都「安装成功」**，表现是「升级命令跑完了、版本却没变」，很容易被误判成发布失败。已实测两轮（隔离目录、`--lockfile-only`，未触碰用户环境）：
>
> 第一轮 pnpm 12.3.4（4.4.x 当时）：
>
> | 目标写法 | 解析到的版本 |
> | --- | --- |
> | 浮动 `^4.4.2` | **4.4.2** ⚠️ |
> | 精确 `4.4.3` | **4.4.3** |
> | 浮动 + `--config.minimum-release-age=0` | **4.4.3** |
>
> 第二轮 pnpm 10.34.5（2026-10-30，5.14.1 发布 11 小时，显式设 `minimumReleaseAge=1440`）：
>
> | 目标写法 | 结果 |
> | --- | --- |
> | 浮动 `^5.13.1` | 解析到 **5.13.1**，**不报错** ⚠️ |
> | 精确 `5.14.1` | `ERR_PNPM_NO_MATURE_MATCHING_VERSION`，明确拒绝 |
> | 精确 `5.14.1` + profile `pnpm-workspace.yaml` 里 `minimumReleaseAgeExclude: [dsh-connect-workbuddy]` | **5.14.1** ✅ |
> | 不设该项（pnpm 默认） | 浮动 `^5.13.1` → **5.14.1** ✅ |
>
> 想立刻用上新版，请写精确版本号：`dsh plugin --profile desktop add dsh-connect-workbuddy@5.20.2`；若被等待期拒绝，见 [`docs/PINNED-UPGRADE-LAG.md`](../../docs/PINNED-UPGRADE-LAG.md) §2 的两条路（等窗口过去，或加那行 exclude）。过了等待期之后，浮动范围会自然跟上。

插件在 **Web**、**Desktop**、**TUI** 三种界面下均可运行，按你使用的 profile 选择对应命令：

```sh
dsh plugin --profile web add dsh-connect-workbuddy     # Web
dsh plugin --profile dsh-tui add dsh-connect-workbuddy # TUI
```

### 安装报 `ERR_PNPM_IGNORED_BUILDS`？先看这条

```
[ERR_PNPM_IGNORED_BUILDS] Ignored build scripts: <某个包>
dsh: plugin command failed; diagnostics: …/operation-xxxx/pnpm.log
```

**这个错误几乎总是别的插件的，不是本插件的。** 本插件的 `dependencies` 只有
`@deepseek-ai/schemastery` 一个，没有任何 `preinstall` / `install` / `postinstall`
脚本，也没有 `optionalDependencies` 或原生模块（`native/turing-sdk/worker.cjs` 是
纯文本 JS）。所以它不可能产生「被拦下的构建脚本」。

那为什么装本插件时会报？**因为 pnpm 每次 `add` 都会重新校验整个 profile 的依赖树。**
如果树里已经有某个包声明了构建脚本、而 pnpm 没有拿到批准，`strictDepBuilds`
（pnpm 11 起的默认值 `true`）就会让**这一整次安装失败**——装的哪个包都一样。实测
在同一个 profile 里装 `dsh-better-sidebar`、`dsh-better-reasoning-effort` 也会报
同一句，而干净的 profile 装本插件是 1.5 秒成功。

**怎么定位是哪个包。** 看报错里 `Ignored build scripts:` 冒号后面那个名字，那是
**别人的包**。例如：

```
[ERR_PNPM_IGNORED_BUILDS] Ignored build scripts: dsh-purge@file:../../vendor/dsh-purge
```

`@file:…` 说明它不是从 npm 装的，而是一个**本地目录**。上面这个路径是相对 profile
目录写的：`<DSH Home>/profiles/<profile>/../../vendor/dsh-purge` 就是
`<DSH Home>/vendor/dsh-purge`。也就是说这个包被放在了 DSH Home 下的 `vendor/` 里，
再由 profile 以 file 协议引用。这类包最容易出问题：它的 `postinstall` 指向的文件
可能没被打进那个目录，于是即使放行，执行时还会报 `Cannot find module …`。

（路径按报错原文推算，用来定位是哪个目录；具体是谁、为什么把包装在那里，得看那个
包自己的安装说明。）

**三条修法，按推荐顺序：**

1. **卸掉那个包**（最干净）——如果它不是你正在用的插件：
   ```sh
   dsh plugin --profile <你的profile> remove <那个包名>
   ```
2. **让 pnpm 不再因为被拒的构建脚本整体失败**——编辑 profile 的
   `pnpm-workspace.yaml`（位置：`<DSH Home>/profiles/<profile>/pnpm-workspace.yaml`，
   Windows 上是 `C:\Users\<你>\.dsh\profiles\<profile>\pnpm-workspace.yaml`），加一行：
   ```yaml
   strictDepBuilds: false
   ```
   这不会执行任何脚本，只是把「有脚本没被批准」从**错误**降级为**警告**。
3. **显式放行那个包**——只有在你确实需要它的构建脚本时：
   ```yaml
   allowBuilds:
     "dsh-purge@file:vendor/dsh-purge": true
   ```
   ⚠️ 两件事：key 必须是**完整标识**——写 `"dsh-purge@file:vendor/dsh-purge"`，
   只写包名 `dsh-purge` 在 pnpm 11 里对 `file:` 依赖不生效（实测仍报同一句）；
   而且放行后会**真的去执行**那个脚本，如果它本身是坏的，你会从
   `IGNORED_BUILDS` 变成 `Cannot find module`——那就回到第 1 条，卸掉它。

> 这三条与 [issue #204](https://github.com/dingminhua/dsh-connect-workbuddy/issues/204)
> 对应。那条 issue 里的自动摘要把原因写成「本插件依赖了原生模块、pnpm 默认拦了它的
> 构建脚本」，**这个归因是错的**——那个 `dsh-purge` 不是本插件的依赖。
>
> 那个自动摘要来自插件市场（`dsh-plugin-hub`）安装器，已在其
> [#583](https://github.com/dshplugin/dsh-plugin-hub/issues/583) 里修正：从 2.2.8 起，
> 当 `Ignored build scripts:` 里的包**全是** `file:` / `link:` 本地依赖时，它不再
> 归因给被装的那个插件（已发布的插件不可能依赖用户 profile 里的路径），改为提示
> 用户自己去 profile 的 `package.json` 里找那些 `file:` / `link:` 条目。混合列表
> （本地 + registry）仍归给作者，因为其中可能真有插件的传递依赖。
