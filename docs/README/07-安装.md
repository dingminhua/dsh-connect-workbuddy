## 安装

前置：已安装并登录 WorkBuddy 桌面 App（插件复用 App 的登录状态）。DSH 需 `0.1.7-rc.1` 及以上；`0.1.5` 及更早请停留在 v2.0.15。

```sh
dsh plugin --profile desktop add dsh-connect-workbuddy    # 推荐
npm install dsh-connect-workbuddy                          # 或 npm
```

安装、更新或卸载 bundle 后需**重启对应的 DSH 进程**。配置入口在**设置面板左侧导航的「WorkBuddy」**（插件市场那个 bundle 详情页从 5.19.0 起不再显示配置卡片，
同一份配置只留这一个编辑入口）。Web / TUI 按 profile 选择：

```sh
dsh plugin --profile web add dsh-connect-workbuddy
dsh plugin --profile dsh-tui add dsh-connect-workbuddy
```

### 版本要求与渠道校验

- **DSH 版本**：支持 `0.1.7-rc.1` ~ `0.1.7-rc.2`、`0.2.x` 正式版（2.1.2 起实测）及实测可用的 `0.2.2-rc.1`~`rc.5`；明确拒绝 `0.3.0-0` 及以上和 `0.1.6` 及更早。
  DSH 的随包门禁逐条核对 `dsh-*` peer 范围，**任一不满足整个包被静默跳过**（provider 不注册、卡片不出现、模型列表清空，页面无报错）。上界写 `<0.3.0-0` 是为了拦住 DSH 从未验证过的 `0.3.0-*` 预发布线。
  详见 [DSH-0.2.2-RC5-FOLLOWUP.md](../../docs/DSH-0.2.2-RC5-FOLLOWUP.md) / [DSH-0.2.1-RC3-FOLLOWUP.md](../../docs/DSH-0.2.1-RC3-FOLLOWUP.md)。
- **国内区渠道校验 400（`code 11128`）请确保插件 ≥ 5.14.0**：5.14.0 起在发请求前按句改写已知固定指纹，旧版实测全部 400（表现为「每次必现、重启也没用」）。

**升级后仍被 11128 拒，按三层处理**（网关按提示词中段任意位置的精确子串匹配，插件改词表只覆盖已知指纹）：

1. **从源头关掉宿主注入的身份句**（`dsh-system-prompt` 配置，写在你自己的 profile 里，三项全关 + 重启宿主 + 开新会话后 11128 消失）：
   ```yaml
   - id: system-prompt
     name: "@deepseek-ai/dsh-system-prompt"
     config:
       includeHarnessIdentity: false
       includeRuntimeContext: false
       personaPrefix: "You are a helpful assistant."
   ```
   改不了配置时，**开全新会话**是有效临时规避（被污染的 assistant 历史写进会话文件、重启也不消失）。
2. **回放的 thinking**：网关扫整份请求文本，多轮会话会把上一轮 `reasoning_content` 原样重发。插件设置项 `dropAllThinking` 打开后不再回放（代价：
   模型看不到自己之前的思考，连续推理任务受影响）；报错里的「零正文指纹线索」会标出 `reasoning_content` 里的命中，据此判断是否需要开。
3. 见[已知限制](16-已知限制.md#已知限制)里跨 provider 的 thinking 处理。

### 刚发布的版本写精确版本号

pnpm 有**新版本等待期**（`minimumReleaseAge`，默认 24 小时）：浮动范围会被静默压回上一个版本，而**两种写法都「安装成功」**，表现为「升级命令跑完、版本却没变」，容易误判成发布失败。
要立刻用新版就写精确号：

```sh
dsh plugin --profile desktop add dsh-connect-workbuddy@5.20.2
```

若被 `ERR_PNPM_NO_MATURE_MATCHING_VERSION` 拒绝，两条路：等窗口过去，或在 profile 的 `pnpm-workspace.yaml` 加 `minimumReleaseAgeExclude: [dsh-connect-workbuddy]`。
过了等待期浮动范围会自然跟上。细节见 [PINNED-UPGRADE-LAG.md](../../docs/PINNED-UPGRADE-LAG.md)。确认升级成功看 `doctor` 第一行或 `status --json` 的 `version`；
装完重启或重载再判断。另：**别把插件市场里的「最新」当日程表**，它读的是会落后的快照，以 `npm view dsh-connect-workbuddy version` 与 [Releases](https://github.com/dingminhua/dsh-connect-workbuddy/releases) 为准（见[更新](08-更新.md#更新)）。

### 安装报 `ERR_PNPM_IGNORED_BUILDS`？

**这个错误几乎总是别的插件的，不是本插件的。** 本插件只有一个依赖 `@deepseek-ai/schemastery`，没有任何构建脚本、optionalDependencies 或原生模块，不可能产生「被拦下的构建脚本」。
原因是 pnpm 每次 `add` 都重新校验整个 profile 的依赖树：树里某个包声明了构建脚本而没被批准，`strictDepBuilds`（pnpm 11 起默认 `true`）就让**整次安装失败**——装哪个包都一样。

**定位**：看报错里 `Ignored build scripts:` 冒号后那个名字。带 `@file:…` 说明是 profile 用 file 协议引用的本地目录（如 `<DSH Home>/vendor/dsh-purge`），
这类包最易出问题：`postinstall` 指向的文件可能没打进目录，放行后仍报 `Cannot find module`。

**三条修法（按推荐顺序）**：

1. **卸掉那个包**（最干净）：`dsh plugin --profile <profile> remove <包名>`。
2. **降级为警告**：在 profile 的 `pnpm-workspace.yaml`（`<DSH Home>/profiles/<profile>/pnpm-workspace.yaml`）加 `strictDepBuilds: false`——不执行任何脚本，
   只把错误降级为警告。
3. **显式放行**（确实需要其脚本时）：`allowBuilds: { "dsh-purge@file:vendor/dsh-purge": true }`。key 必须是**完整标识**（只写包名对 `file:` 依赖不生效）；
   放行后会真的执行脚本，脚本坏则从 `IGNORED_BUILDS` 变成 `Cannot find module`，回到第 1 条。

> issue #204 的自动摘要曾把原因错写成「本插件依赖原生模块、pnpm 拦了构建脚本」——那个 `dsh-purge` 不是本插件的依赖。插件市场安装器已在 [#583](https://github.com/dingminhua/dsh-plugin-hub/issues/583) 修正：从 2.2.8 起，当被拦的包全是 `file:`/`link:` 本地依赖时不再归因给被装插件。

### 平台支持

三个平台都是受支持目标，**Windows 是一等目标平台**：CI 在 `windows-latest` 跑完整套件，凭据路径、进程心跳、App 定位、设置写入四处都有 Windows 专属分支与测试，
修复只对 Windows 生效的缺陷时以用户现场真机取证为准。各平台差异见[平台支持](09-平台支持.md#平台支持)。
