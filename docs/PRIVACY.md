# 隐私与脱敏（Privacy）

> 本文档是 `dsh-connect-workbuddy` 的**唯一权威隐私规则**。改截图、写文档、写 issue 回复、发布新版本前都读一遍。
>
> **不违反它比修一个新 bug 更重要**：代码缺陷可以打补丁再发一版；一张没打码的截图一旦推上 GitHub 或被 `npm publish` 打包，
> 就再也收不回来了（npm 的旧 tarball 永久可下载，git 历史可被任何人 clone）。
>
> 本文档**随包发布**（在 `package.json` 的 `files` 白名单内），因为它是给下游使用者的承诺，不只是维护者备忘。

## 0. 一句话规则

**凡是「真实账号、真实机器、真实会话」留下的痕迹，都不许进仓库，也不许进发布包。**

判据只有一条：**这段内容能不能被反向还原到一个具体的人、账号、设备或会话？** 能，就必须脱敏或删掉。

## 1. 受管的内容面

本项目的隐私暴露面分五类，**每一类都要单独检查**（只查其中一类是过去漏掉的直接原因）：

| 类别 | 典型载体 | 是否进发布包 |
| --- | --- | --- |
| **截图** | `docs/assets/*.png`、`docs/pr188-mac-shots/*.png` | `docs/assets` 进；`pr188-mac-shots` 不进但仍在公网仓库 |
| **文档正文** | `README*.md`、`CHANGELOG.md`、`docs/**.md`、issue 回复草稿 | 部分进 |
| **设计稿 / 演示页** | `docs/*.html`、`docs/assets/*.html` | 不进发布包，但**在公网仓库里** |
| **测试固件** | `tests/*.spec.ts` 里的 `uin` / `nickname` / 邮箱 | 不进发布包，但在公网仓库 |
| **构建产物** | `lib/*.js`（打包会把源码字符串带进去） | **进** |

> ⚠️ **「不进发布包」不等于「不暴露」**。`docs/pool-header-redesign.html` 不在 `files` 白名单里，
> 但它躺在公开仓库的 `main` 分支上，任何人 `git clone` 就能读到。**判断标准是「公网可读」，
> 不是「在 npm 包里」。**

## 2. 绝对禁止出现在仓库任何地方的内容

下面每一条都是**无条件禁止**，没有「这次例外」：

- **完整手机号**。任何 11 位中国大陆手机号，无论是否加引号、是否在代码块里、是否在 `docs/`、`docs/audit/`、
  测试固件、HTML 演示页、CHANGELOG 引用里。**这是本项目历史上真实发生过的一类泄露。**
- **完整邮箱**。维护者本人的邮箱也不行——GitHub commit 的 `Author` 已经公开的是既成事实，
  但**正文、测试固件、注释里不许再出现任何完整邮箱**。需要举例时写成 `someone@example.com`。
- **真实 uin / uid / enterpriseId**。WorkBuddy 的 `uin` 是账号级持久标识符（一串 9–12 位数字）。
  写测试用 `1`、`100000000001` 这种显然的假值；**永远不要**把真机日志里的数字粘进来。
- **access token / refresh token / cookie / `X-Device-Token`**。哪怕是「已经过期」的、哪怕是「只截了一部分」的。
  需要举例时写 `at-fixture`、`token-alpha-old` 这类明显的假值。
- **本机绝对路径里的用户名**。macOS 的 `/Users/<用户名>/…`、Windows 的 `C:\Users\<用户名>\…` 都不行。
  写文档时一律用占位：`/Users/<you>/...`、`C:\Users\<you>\...`、`<repo>`。
- **会话 id / 设备 id / 指纹**。`session-<uuid>`、设备指纹产物。需要说明时用 `<session-id>` 占位。
- **真实昵称**。上游返回的账号显示名（中文昵称形如「老+姓」，英文形如 `Lao` 前缀的拼写，
  以及「用户 + 一长串数字」这种自动生成名）出现在截图或文档里，等于公开「哪个账号在给这个插件做测试」。
  版权行里的 `Copyright (c) 2026 LaoDing` 是**许可证主体**，不受此条约束（见 §5）。

## 3. 截图规则（过去翻车最多的一类）

### 3.1 打码必须「不可逆」

- ✅ **不透明纯色块覆盖**。最简单、最安全，也最容易被读者看出「这里被脱敏了」。
- ✅ **裁掉整个区域**。账号列、余额列可以整列裁掉，只要截图仍能说明问题。
- ❌ **马赛克 / 像素化**。小色块（≈4–10px）在马赛克边缘仍可能残留字形轮廓；而且本项目历史上用过
  **半透明**的马赛克（最暗处 199/255，不是黑），意味着下方原始像素参与了混合——**理论上存在被复原的风险**。
  以后一律不再使用马赛克。
- ❌ **高斯模糊**。小半径模糊是可以被反卷积攻击的；而且看不清的字形仍可能泄露字符数、词长。
- ❌ **半透明遮罩**（`opacity < 1` 的方块、带 alpha 的 PNG 矩形）。

### 3.2 打码之前先看画布边缘

**被裁切不等于被脱敏。** 本项目出过这样一次：模型选择器截图的**画板顶边**残留了一行账号号码——
它被上边缘切掉了一半，但上半截字形完好可读，而图片的 `alt` 文案还写着「无账号信息」。

规则：

- 截图前把**画板上边缘、下边缘、左右边缘各留 8px 空**，不要让任何内容贴在边上。
- 出图后**逐边检查**：把图放大到 400%，看四条边上有没有被切掉一半的文字。
- 一次截图里如果包含了账号表格，**默认整块不要**，而不是「先截下来再打码」——后者迟早漏一行。

### 3.3 打码之后要复核

改完图必须**重新读一遍成品**（不是看源文件、不是看命令行输出），确认：

- [ ] 所有真实账号名、手机号（含掩码形式 `1XX****XXXX`）、uin、昵称都不可读
- [ ] 没有残留的「半截字」贴在画布边缘
- [ ] 图片的 `alt` 文案与图里**实际**有没有账号信息**一致**（写着「无账号信息」就必须真的没有）
- [ ] 图片元数据干净（见 §4）

> ### ⚠️ 最容易漏的一处：整窗截图的**左下角**
>
> 本项目第二次审计就是这样漏掉的：账号表格已经盖住了，但 DSH 侧栏**左下角那个头像 + 昵称**
> 原样留在画面上，五张 PR188 真机截图里全都是。**它不是账号表格的一部分，所以「我盖了账号列」的
> 自查会直接跳过它。**
>
> 整窗截图（DSH 界面、任何 Electron 应用）必须先扫这四处再动手：
>
> | 位置 | 里面有什么 | 处理 |
> | --- | --- | --- |
> | **左下角** | 登录用户的头像与昵称 | **必须盖**——这是账号身份 |
> | **左栏工作区列表** | 你的项目目录名（本项目旧截图里就有 `ld-mouse`、`dsh-xw` 等） | **必须盖**——除非截图本身就在说明「左侧有哪些行」 |
> | **左栏会话标题** | 你历史对话的标题（会暴露你在做什么） | **必须盖**——同上 |
> | **窗口标题栏 / 顶栏** | 有时带用户名或主机名 | 必须盖 |
>
> **`scripts/check-pii.mjs` 看不见这些**——它们是像素，不是文本。这一条只能靠人眼。
>
> **一处明知故留**：`docs/pr188-mac-shots/` 那五张截图保留了左栏的工作区名与会话标题。
> 它们是**那几张截图要说明的东西**（「侧边栏那一行有没有 WorkBuddy」只能靠对照左栏看出来），
> 盖掉之后截图就证明不了任何事。这是一次**显式的、被记录的取舍**，不是遗漏；
> 同类取舍必须写进 CHANGELOG，不能默默做过。

> **掩码形式要不要打？要。** `1XX****XXXX` 虽然只有 3+4 位可见，但它与 `tests/` 里的固件、
> CHANGELOG 里的引用一交叉就能定位到具体账号；而且截图里的掩码旁边往往还有余额、过期时间构成的指纹。
> **一律打成实心块。**

## 4. 图片元数据

PNG 的 `tEXt` / `iTXt` / `zTXt`、JPEG 的 EXIF / XMP 都可能带上拍摄设备、用户名、绝对路径。
本项目目前所有截图元数据是干净的（已逐张核对），但**每次新增图片都要查**：

```bash
node scripts/check-pii.mjs          # 会列出每张图的元数据块
```

含 `tEXt` / `EXIF` / `XMP` 的截图必须先用工具剥离元数据再入库。

## 6. 发布前的强制核对

**这一步是发布流程的一部分，写在 [`RELEASING.md`](../RELEASING.md) 第 2.7 步，不得跳过。**

```bash
node scripts/check-pii.mjs
```

脚本退出码非 0 就不许发布。它检查：

1. 发布包内的每个文本文件（`files` 白名单）里的手机号、邮箱、token、本机路径、uin
2. 仓库内全部文本文件（含 `docs/`、`tests/`、HTML）里的同上内容
3. 每张图片的元数据块
4. 图片文件名与 `screenshots.json` 的登记

**自动扫描只能挡住它认识的模式。** 新增一类内容（比如第一次截图浏览器开发者工具、第一次贴真机日志）时，
必须**人工再看一遍**，并把新发现的模式补进 `scripts/check-pii.mjs` 的规则表。

## 7. 漏了怎么办

1. **立刻改正文件并提交**——公网仓库的 `main` 是最先要修的地方。
2. **发一个新补丁版本**——npm 上旧的 tarball 永久可下载，只有新版本能覆盖「最新版」这个入口；
   要发新版本必须在 `CHANGELOG.md` 里**如实写明泄露了什么**（不要含糊成「若干文档修正」）。
3. **不要试图悄悄抹掉**。历史提交（`git log -p`）仍然能查到；如果确实需要清理，
   用 `git filter-repo` 重写并强推，同时**在 CHANGELOG 与 Release 里说明这次重写**——
   否则下一个 clone 的人会以为仓库一直很干净，重复同样的错误。
4. **不需要恐慌性轮换 token**：本插件**从不把 token 写进仓库**（`$DSH_HOME/workbuddy-vault/` 与
   `~/.dsh/.workbuddy-auth.*.json` 都在 gitignore 之外的用户目录）。泄露的是**显示名与号码**，不是凭据。
   但如果确实有 token 进过仓库，那必须轮换，且优先级高于本文档所有其它条目。

## 8. 写给 AI 助手

用 AI 代跑发布或代写文档时，**它默认不会主动检查隐私**——它会把真机日志、真实截图路径、完整号码
原样写进文档。所以：

- 让 AI 写任何含「真机」「实测」「截图」的内容时，**明确要求它只写占位符**。
- AI 生成的文档入库前，**自己跑一遍 `node scripts/check-pii.mjs`**，不要只信它的自我描述。
- AI 代跑发布时，[`RELEASING.md`](../RELEASING.md) 第 2.7 步**必须**由人确认结果，不能只看它的「已完成」。
